2　模型推理 84.7%：拆解与鲲鹏加速

拆解口径：测试集群 48 题共 454 轮模型调用（每题 9.5 轮，每轮平均 4.6 秒），按每轮的消息时间戳拆成「首 token 前」与「生成」两段； 首 token 前再按每轮的新增 token 与命中缓存的 token 数做回归，分出固定开销、缓存前缀加载、新增 token 预填充。被测模型为公网 DeepSeek（已自带前缀缓存，命中 94%），私有化部署到鲲鹏 + 昇腾后需重测。

每轮送入约 4 万 token其中 3.7 万命中前缀缓存，新增约 2,500
每轮生成约 650 token含思考、工具调用参数与回答
首 token 前1.27 s / 轮固定开销 0.92 + 缓存加载 0.29 + 预填充 0.06
生成3.3 s / 轮约 195 token/s

84.7% 由四段组成（占端到端时间）

生成（decode）61.2%
固定开销 17.1%

从左到右：生成 61.2% · 到推理服务的固定开销（往返、排队、调度）17.1% · 缓存前缀加载 5.4% · 新增 token 预填充 1.0%；合计 84.7%。

子环节占端到端每轮在做什么鲲鹏怎么加速提升多少（待填）可佐证的指标
A　生成（decode）61.2%3.3 s 逐 token 生成思考、工具调用参数与回答，约 650 token / 轮；受显存带宽与并发组批大小限制
  • KV Cache 卸载到鲲鹏主机内存（MindIE KV 池化 / GMEM）：腾出昇腾显存，同一台推理服务器能组更大的并发批次，满额时排队更少、吞吐更高
  • 部分 decode 卸载到鲲鹏 CPU（openEuler sysHAX）：鲲鹏与昇腾协同分担生成
  • 消除主机瓶颈：每个 token 步的调度、采样在鲲鹏主机上完成，推理进程按 NUMA 亲和绑到离 NPU 最近的鲲鹏核
  • 鲲鹏 950：SVE2 与 INT8 矩阵向量吞吐优化、内存带宽提升 2.25 倍，CPU 侧分担生成更强
 每 token 时延；满额并发生成吞吐（token/s）
B　固定开销17.1%0.92 s 每轮请求到推理服务的往返、排队、调度与组批，与 token 数无关；每题 9.5 轮，累积起来不小
  • 池化集群与推理服务器同架构、同机房：Atlas 800I A2 主机就是 4 路鲲鹏 920，池子也在鲲鹏上，经 RoCE 直连（整机 8 × 200GE），去掉跨域与公网往返
  • 鲲鹏主机多核负责请求接入、分词、组批调度，128 人并发时不排队

合计84.7%4.6 s每题 9.5 轮 × 4.6 秒 ≈ 43.3 秒每题模型时间
  • 为什么必须用鲲鹏主机内存：每轮约 4 万 token 的上下文要靠前缀缓存复用。按 DeepSeek-V3 结构估算，每个 token 的 KV Cache 约 69 KB， 128 人同时在线约 128 × 4 万 × 69 KB ≈ 350 GB；一台 Atlas 800I A2 的 8 个昇腾模组显存合计 256 GB，且大部分要放模型权重。 放不下的缓存一旦被挤出，每轮就要把约 4 万 token 整段重算——C 段的 0.29 秒会变成数秒。鲲鹏主机的 32 条内存插槽正好做这一级。
  • 收益最大的是 A 和 B：生成（61.2%）靠「显存腾给更大的并发批次 + 鲲鹏分担」，固定开销（17.1%）靠「池化与推理同架构、同机房直连」。
