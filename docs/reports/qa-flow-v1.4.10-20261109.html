1 一次提问依次经过的步骤

1 提问进入→2 分配槽位→3 建会话、发问→4 组装上下文→ 5–6 模型推理 ⇄ 7–11 工具(每题约 7.7 轮)→13 输出回答→14 存档与回写(后台)

第 5–11 步是一个循环:模型每一轮读完整段上下文,决定调哪个工具或直接回答;工具结果回灌进上下文,进入下一轮,直到模型给出最终回答。下表是 18 次对话的每题平均。

3 token 都花在哪

每一轮都要把「系统提示词 + 根提示词 + 技能说明 + 之前所有轮的工具结果与回答」整段送给模型,所以送入 token 随轮次增长; 模型服务对重复的前缀做了缓存,90.9% 的送入 token 命中缓存、不重新计算,真正新增的只有每题约 2.3 万。输出 token(思考 + 工具参数 + 回答)每题约 4,834,是时间的大头(见第 2 节「生成」)。

6 观察

  • 时间主要花在模型上:模型推理占 81.8%(生成 63.8%、首 token 前 18.1%),工具执行 17.9%,opencode 编排 0.3%;接入网关、建会话、组装上下文都在毫秒级。
  • 最后一轮写回答几乎占一半时间:最后一轮(首 token 前 + 生成)占全部时间的 48.7%。回答越长、思考越多,这一段越长。
  • 思考占输出的大头:输出 token 里 58.7% 是模型的思考,其余是工具调用参数与回答正文;生成速度约 155 token/秒。
  • 每多一轮多约 1.1 秒固定开销:每轮等第一个字约 1.14 秒(中位 1.10 秒),与送入多少 token 关系不大(送入 2.5 万以下与 4 万以上的中位只差约 0.1 秒,前缀缓存让长上下文不必重算);每题 7.7 轮,合计约 8.8 秒。轮数越少越快。
  • 送入 token 多,但九成命中缓存:首轮送入约 2.0 万(系统提示词、根提示词、技能清单、工具定义),之后每轮带上之前全部内容,末轮到 3–7 万;90.9% 命中前缀缓存。每加载一份技能说明,下一轮新增约 7,468 token。
  • 取数最重的是健康检查与内存定位:全面健康检查时 health.py 一次调中间件 58 次、用时 13–19 秒(子技能与各项取数依次执行);memanalyze.py 平均 29 次、10.0 秒;每次中间件调用约 0.32 秒(测试环境的模拟中间件与网关同机)。行内真实中间件每次调用更慢时,这两类题的工具时间会按调用次数成比例变长。
  • 技能脚本进程启动不是瓶颈:每次起 Python 进程加导入约 0.19 秒,每题约 6.2 次,合计约 1.2 秒。
  • 和 v1.4.3 的测量量级一致:鲲鹏池化方案里用 48 道验收题测得每题 51 秒、9.5 轮、模型占 84.7%、每轮送入约 4 万 token、命中 94%;本次每题 48.9 秒、7.7 轮、模型占 81.8%、每轮送入约 3.3 万、命中 90.9%。两次题目不同,只比量级、不比快慢。

7 怎么测的

  • 环境:agent-v1.4.10;单机 Kubernetes(arm64),网关 2 副本,固定池 3 Pod × 3 槽位;opencode 1.18.27;模型 DeepSeek(deepseek-flash,公网接口);中间件为模拟服务(签名校验开,与网关同机);数据库为 openGauss-lite 5.0.3 测试库(og5);用户入口为模拟统一认证 + 端口转发。
  • 题目(诊断、问答、红线各类都有,都是只读):
    1. Q1 全面健康检查:对 og5 做一次健康检查。
    2. Q2 快速概况:og5 现在怎么样?
    3. Q3 慢 SQL 排行:给我 og5 最近的慢 SQL 列表。
    4. Q4 参数体检:og5 的参数配置有没有问题?
    5. Q5 实时定位(内存):og5 内存使用很高,是谁占的?
    6. Q6 存储过程诊断:og5 上的存储过程 fl.fl_slow_key 跑得很慢,帮我看看哪里慢、怎么改。
    7. Q7 知识问答:lockwait_timeout 默认是多少?DDL 等锁也受它控制吗?我们行里做 DDL 变更有什么要求?
    8. Q8 案例检索:单条 update 平时几毫秒,偶尔要好几秒,我们行以前遇到过吗?是什么原因?
    9. Q9 红线(要求改参数):帮我把 og5 的 shared_buffers 改成 16GB。
  • 采集:经用户入口(模拟统一认证 → 网关 → 本人槽位里的 opencode)新开对话发问,等答完后取会话全部消息。每轮模型调用的创建 / 完成时间、 第一个思考或正文片段的时间、每次工具调用的起止、每轮 token(新增、命中缓存、输出、思考)都是 opencode 记下的原始数据;同一时刻只问一题,避免互相干扰。
  • 口径:耗时 = 用户消息创建到最后一轮完成;token 是模型服务返回的计数。不含用户读回答、思考下一句的时间。
  • 局限:中间件是测试环境的模拟服务(与网关同机、库是小型测试库),行内真实中间件与生产库每次调用会更慢,第 9 步在行内会更长; 模型走公网 DeepSeek,首 token 前与生成速度随服务方负载波动;每题只问 2 次,单题数字仅供参考,看占比与量级。
