## 一、本版内容(技能包)

背景(2026-11-25 现场反馈):健康检查在 8 个库里 6 个报「无法识别的布尔取值 '[B@276fe535'」。业务库是 M 兼容模式时,中间件按 JDBC 类型映射
取值再转成文字,布尔列取回来是 Java 字节数组 `[B@…`、原值丢失。v1.5.1 修的是 SQL 能否执行,这是下一层:取回来的值。

1. **业务库脚本的输出列收口**:在业务库执行的脚本,输出列一律是《GaussDB M-Compatibility 开发指南》JDBC 映射表里取出来就是文字 / 整数 / 小数的类型——
   布尔列输出 1/0(`CASE WHEN … THEN 1 ELSE 0 END`),名字类(name)与 `"char"` 列 `::text`,表达式列都写别名。列名一律不变;A 兼容库上取值与 v1.5.1
   一致(布尔由 true/false 变为 1/0,技能两种都认)。登录探针 `login.current_db` 不改(现场已证实它的库名列在 M 库上取值正常)。
   受影响的技能:健康检查 Schema / WAL 维度、SQL 调优与存储过程调优的索引信息、vacuum 报错;SQL 审查(每张表被判成「没有主键」)与
   存储过程定位(schema 被判成没有 USAGE)原先不报错但结论错。
2. **新增 `sqltune.plan_yaml`**:YAML 格式的执行计划(输出列是 text 类型,内容与 JSON 同构)。M 库上 JSON 计划(json 类型)取不到原值时,
   SQL 调优的代价推演改用它。
3. **布尔解析一律严格**:认不出的取值报错并写明原因,不再静默当成「否」。
4. **部署自检 `--m-trial`**:除了报不报错,逐列检查取回来的值,出现 `[B@…` 判失败。

**未改动**:提示词(根提示词与各技能说明)、依赖(Python 包、系统程序)、配置文件格式、环境变量;除下表以外的技能、脚本定义与公共模块;
`rootspec/`;各技能版本号。

**升级**:先把 `whitelist/scripts-delta-20261125.sql` 导入中间件(还在 v1.5.0 白名单的先导 20261123;更早的按 README 的顺序),再整包换技能包
(覆盖前备份 `common/config.yaml`、覆盖后还原);新开对话,运行一次部署自检,业务库是 M 兼容的加 `--m-trial`,把输出发回核对。
