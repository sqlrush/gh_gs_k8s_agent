# 版本说明

每个版本的镜像标签是 `agent-v<版本>-oc1.18.27`（`oc1.18.27` 是镜像里的 opencode 版本）。
升级步骤见《部署手册-从零到上线》§10.5：用户容器在下次登录时换新版，正在用的人不受影响。

## agent-v1.5.3（2026-11-26）

**老浏览器上的对话页、三条报错提示。** 2026-11-26 现场：Windows 7 上的 Edge 109、360 企业安全浏览器 V13（Chromium 108 内核）打开对话页，
回答里的行内代码（SQL 编号、函数名、技能名）显示成黑块；新部署的容器版登录数据库只回「调用方不存在」，模型把它猜成库名问题。
本版在网关给对话页加老浏览器兼容补丁，并让三处报错说清原因。**白名单不变（仍 133 条），从 v1.5.2 升级不用导增量**；提示词没有改；
按需、固定池化、Fuyao 三种模式的行为不变，可以用发版台升级。

### 升级前先看

| 要做的事 | 为什么 |
|---|---|
| 白名单**不用导**。还在 v1.5.1 白名单（132 条）的，先导 `scripts-delta-20261125.sql`（见 v1.5.2） | 本版没有改脚本 |
| 用技能包（`diag` 分支）装在自有环境的：整包替换（`common/`、`scripts/`、`skills/`），覆盖前备份 `common/config.yaml`；新开对话 | 本版改了公共代码与两个技能的脚本；提示词未改 |
| **五个镜像**与 `USER_IMAGE_TAG` 一起改成 `agent-v1.5.3-oc1.18.27`；`k8s/base/kbstd-install.yaml` 的 Job 名改成 `kbstd-install-v1-5-3`，两处 `image:` 也指到新标签 | 网关镜像带了兼容补丁；标准知识库内容不变，新 Job 跑一次即「同版本跳过」 |
| 删掉现有的知识库导入容器：`kubectl -n gaussdb-agent delete deploy,svc -l role=kb-import`（NAS 上的数据不动；发版台自动做） | 导入镜像里的公共代码换了 |
| 网关多了一个可选配置 `LEGACY_COMPAT`（gateway-config，默认开，填 `"0"` 关）。重新 `kubectl apply -k` 一次让网关带上这个映射；不 apply 也是开着的 | 见下文「对话页老浏览器兼容」 |

### 改了什么

- **对话页老浏览器兼容（网关）**：对话页（opencode 自带的网页）给行内代码设背景色分两步——先设成与文字同色兜底，再用 `color-mix()` 调成浅底色；
  `color-mix()` 要 Chrome / Edge 111 以上，老内核丢掉这一句，只剩兜底，于是黑底黑字（内容没丢，选中能看见）。opencode 1.18.27 的样式里这样的
  `color-mix()` 有 94 处，另有 18 处 `light-dark()`（123 以上）。网关转发对话页入口时在 `<head>` 前引用一段补丁脚本
  （`/__agent/legacy-compat.js`，网关自己出，同源，opencode 的安全策略放行），在老浏览器上把这些颜色换算成老内核认的写法，`light-dark()` 按页面当前的深浅色取值，
  并补上老内核缺的几个脚本接口。**新浏览器上补丁什么都不做。** 只改对话页入口这一个页面；接口、事件流、报告页、大盘原样转发。不改 opencode、不改技能。
- **「调用方不存在」**：中间件认不出调用方时只回这一句。现在报错后面带提示——核对智能体配置里的 `GRMP_APPKEY`（整个智能体一个，不能留空；
  留空时智能体根本不带 Appkey）与本人令牌 `grmp-token-<工号>`，与库名、实例、SQL 无关，不要让 DBA 改库。
  《快速搭建-Fuyao沙箱》里 `GRMP_APPKEY` 原先默认留空，现改成要填（漏填检查能拦住），常见报错速查加了这一条。
- **内存分析 WLM 层只回「执行失败」**：L4 / L5 经中间件只回「agent诊断脚本执行失败」（不带数据库原文）时，说明最常见原因是执行账号没有 WLM 资源跟踪函数的权限，
  并按各层读的视图给 DBA 一条当场能验证的 `SELECT count(*) FROM gs_wlm_…`。原先只在原文带 permission denied 时才这样提示，经中间件时这条提示一次也没出现过。
- **部署自检 `--m-trial`**：业务库名单里没有技能调用的 `perf.locks`、`perf.table_stat` 标「本版不交付」、不试跑。原先技能包里报
  「读不到本地脚本定义（scripts/ 没放进技能目录）」，原因写错（1.5.1 起）。

### 验证

- **真实 Chromium 108 内核**（与 360 企业安全浏览器 V13 同一内核版本；Edge 109 比它新一版）打开 opencode 1.18.27 对话页的同一个会话：
  不打补丁时 5 处行内代码的底色与字色都是 `rgb(22, 22, 22)`，与现场照片一致；打补丁后底色是 8% 的浅灰、文字可见，与新浏览器的样子一致，页面零报错。
- 网关单元测试覆盖两条转发路径（固定池化 / Fuyao、按需建）：只改 GET 200 的未压缩 HTML、长度重写、安全策略头不动；接口、事件流、压缩过的页面、报告页、大盘原样；
  补丁脚本照样要先认人；`LEGACY_COMPAT=0` 能关。
- 三处提示：各自的单元测试在修复前失败、修复后通过。
- 单元测试全部通过。

## agent-v1.5.2（2026-11-25）

**业务库 M 兼容第二轮：取回来的值。** 2026-11-25 现场：健康检查在 8 个库里 6 个报「无法识别的布尔取值 '[B@276fe535'」。
1.5.1 修的是 SQL 能不能执行（那条脚本在 M 库上已经执行成功），这次暴露的是下一层：业务库是 M 兼容模式时，中间件按 JDBC 类型映射取值再转成文字，
布尔列取回来是 Java 字节数组 `[B@…`，原值丢失。本版把在业务库执行的脚本的输出列全部改成 M 兼容库能原样取回的类型。
从 v1.5.1 升级；更早的版本先按各自的说明升到 v1.5.1 的白名单，再导本版增量。提示词没有改；按需、固定池化、Fuyao 三种模式的行为不变，可以用发版台升级。

### 升级前先看

| **五个镜像**与 `USER_IMAGE_TAG` 一起改成 `agent-v1.5.2-oc1.18.27`；`k8s/base/kbstd-install.yaml` 的 Job 名改成 `kbstd-install-v1-5-2`，两处 `image:` 也指到新标签 | 标准知识库内容不变，新 Job 跑一次即「同版本跳过」 |

### 现场问题与影响范围

在业务库执行、直接返回布尔列的脚本共 7 条（交付 6 条），M 兼容业务库上 1.5.1 的表现：

| 技能（脚本） | 1.5.1 在 M 兼容业务库上 |
|---|---|
| 健康检查 Schema 维度（`health.unused_index`） | 报「无法识别的布尔取值」（现场照片） |
| 健康检查 WAL 维度（`health.table_writes`） | 同上 |
| SQL 调优（`sqltune.indexes`）、存储过程调优（`proctune.indexes`） | 取索引信息时报错，调优跑不完 |
| vacuum（`vacuum.dead_tuples` 的表级 autovacuum 开关） | 报错 |
| SQL 审查（`sqlreview.tables`、`sqlreview.indexes`） | **不报错但结论错**：每张表都判成「没有主键」、索引都判成非唯一 |
| 存储过程定位（`procinfo` / `proctune.locate_schema` 的 schema 权限） | 不报错，schema 判成「没有 USAGE 权限」 |

另外，SQL 调优的「代价推演」用的 JSON 格式执行计划（json 类型）在 M 库上同样取不到原值，推演做不了。

### 改了什么

- **输出类型收口**：在业务库执行的 42 条脚本，输出列一律是《GaussDB M-Compatibility 开发指南》JDBC 映射表里取出来就是文字 / 整数 / 小数的类型——
  布尔列输出 1/0（`CASE WHEN … THEN 1 ELSE 0 END`），名字类（name）与 `"char"` 列加 `::text`，表达式列都写别名。列名不变；
  A 兼容库上取值与 1.5.1 一致（布尔由 true/false 变为 1/0，技能两种都认）。登录探针 `login.current_db` 不改：现场已证实它的库名列在 M 库上取值正常。
- **新增 `sqltune.plan_yaml`**：YAML 格式的执行计划，输出列是 text 类型，内容与 JSON 同构。M 库上 JSON 计划取不到原值时，代价推演改用它。
- **布尔解析一律严格**：认不出的取值报错并写明原因（遇到 `[B@…` 直接说明「中间件按 Java 对象转了文字、原值已丢失」），
  不再静默当成「否」——SQL 审查、存储过程定位原先就是这样把错的结论报出去的。
- **部署自检 `--m-trial` 检查取回来的值**：除了报不报错，出现 `[B@…` 的列逐条列出。1.5.1 的试跑只看报错，所以没发现这个问题。
- **守卫**：新增业务库脚本的输出类型清单（连 A / B 兼容测试库实测，含每条脚本正文的摘要，`agent/tools/registry_output_types.py` 生成）
  与守卫测试 `test_registry_output_types_units.py`——脚本正文一改就要求重测类型，类型不在安全集合里、表达式列没有别名都会失败。

### 为什么 1.5.1 没测出来

1.5.1 的模拟测试用 gsql 直接执行 SQL、看文本输出，只验证了「能不能执行」，经过不了「中间件按类型取值再转成文字」这一层。
本版给模拟中间件加了 `--m-jdbc`：连到 B / M 兼容库时，按现场中间件的方式把映射表以外类型的列渲染成 `[B@…`，以后的 M 兼容验证都经过这一层。

### 验证

- 开启 `--m-jdbc` 的模拟中间件 + openGauss 7.0 的 B 兼容库上跑 1.5.1：健康检查报出与现场照片相同的「无法识别的布尔取值 '[B@…'」，
  SQL 调优、vacuum 报错，SQL 审查把每张表判成「没有主键」——问题完整复现。
- 同一环境跑 1.5.2：健康检查、SQL 调优（含代价推演）、执行计划、存储过程调优、过程定义、SQL 审查、vacuum、Top 过程、锁等待、内存分析
  10 个技能在 A、B 两种库上都正常，结论一致（差异只在两个库各自的统计值）；`--m-trial` 在 B 库上 39 条通过、3 条按设计不适用。
- 42 条业务库脚本：A 库上 1.5.1 与 1.5.2 逐行一致；B 库上 1.5.2 全部可执行、取值与 A 库一致。
- 单元测试全部通过。

**仍以现场为准**：升级、导完增量后，请在 M 兼容业务库上跑一次 `selfcheck.py --session <句柄> --m-trial`，把输出发回。

### 现场报错的 15 条脚本

| 脚本 | 原因 | 处理 |
|---|---|---|
| `health.unused_index`、`health.stale_stats`、`lockwait.pairs`、`explain.kernel_funcs` | `\|\|` 在 M 库是逻辑或 | v1.5.0 已改 `concat`；本版名字类列再显式转成文字。`health.stale_stats` 另去掉 M 库 CAST 不认的 `float8` |
| `health.partitions` | `max()` / `COALESCE()` 处理 `"char"` 列报 un support type | 先用 CASE 映射成文字再聚合，输出不变 |
| `health.table_writes` | 两个 name 类型取 COALESCE 推导成 any，报 `any <> unknown` | 改成一层查询；原外层的 `"table"` 在 M 库是字符串常量（修好前一处后整列会变成字面值），一并去掉 |
| `sqlreview.tables`、`sqlreview.indexes` | `TABLE` 是 M 库保留字，`AS table` 报语法错 | 别名改 `AS "table"`；去掉 `ARRAY[]` 字面量，索引列顺序改用 `position` |
| `procinfo.locate_search`、`proctune.locate_search` | M 库不支持 `ILIKE` | `lower(…) LIKE lower(…)` |
| `procinfo.source_adm`、`proctune.source_adm` | M 库没有 ADM_SOURCE 视图（只继承了部分系统视图） | 无对等写法，脚本不改；技能在 M 库上不再调用，报告写明原因 |
| `memanalyze.wlm_sql`、`wlm_operator`、`wlm_operator_hist` | 执行账号没有 WLM 函数权限（在 postgres 库执行，不是兼容问题） | 脚本不改；原因写成「执行账号没授权」，照旧改从 SQL 执行历史取 |

同类写法（名字类列进 `concat` / `COALESCE`）另改了 `procinfo.proc_def`、`proctune.proc_def`（交付）与 `perf.locks`、`perf.table_stat`（不交付）。
列名一律不变，调用方代码不用跟着改。守卫测试按官方文档《M-Compatibility 开发者指南》的规则检查全部 41 条业务库脚本：不许 `ILIKE`、
M 保留字裸别名、表达式里的双引号名、`ARRAY` 字面量、M 不认的 CAST 类型、`concat` / `COALESCE` 里不带 `::text` 的名字列、`ADM_*` 视图。

### 识别业务库兼容模式

- 登录时探针 `login.current_db` 顺带取 `datcompatibility` 与 `lower_case_table_names`，登录输出加「兼容模式」一行（切到业务库时）；
  白名单增量没导时写「未知，按 A 兼容处理」。会话里存在旁挂文件 `<句柄>.compat`，回滚到旧版照常可用。
- M 库上：存储过程源码不再走 ADM_SOURCE 兜底；EXPLAIN 前的语句检查同时按 A、M 两套词法切（`#` 注释、反斜杠转义后面藏第二条语句的写法都拦下；
  A 库只按 A 规则，与 v1.5.0 相同）；从 SQL 里取表名、补 schema 认反引号，表名是否折小写看 `lower_case_table_names`，补的 schema 用反引号；
  SQL 审查按 MySQL 词法切分（双引号是字符串、`#` 是注释）。
- SQL 调优、存储过程调优、SQL 审查的报告开头写「业务库兼容模式：M」（只在 M 库出，A 库报告与 v1.5.0 一字不差）。
- 部署自检加「业务库兼容模式」一项；`--m-trial` 把 41 条业务库脚本用安全参数（不存在的对象名、`SELECT 1` 的估算计划）各试跑一次，只读。

### 提示词（小改）

- 根提示词「数据库连接规则」加第 5 条（3 行）：按登录输出的「兼容模式」写改写 / 建索引 / 示例语句；M 库用反引号、`concat()`，
  不用 `ILIKE`、`||`、`::`、双引号标识符；未知时按 A 库写并说明。
- SQL 调优、存储过程调优的技能说明各加半句：M 兼容库查新增的 `references/gaussdb-m-compat-gotchas.md`（每条注明官方文档出处）；
  SQL 审查的技能说明改 1 句（「不加引号的名字折成小写」只对 A 库成立）。

**新增第三种运行方式 `RUNTIME_MODE=fuyao`**：在 openFuyao 沙箱平台上每人一台微型虚拟机（诊断、导入各一台）。

### 改动

- **切到业务库（dbName）**：登录时给了业务库名（`--ip … --database <库名>`，或 `--alias <别名> --database <库名>`），对象类取数——
  执行计划、表结构、索引、列统计、统计信息新鲜度、死元组与膨胀、存储过程定位与源码、锁等待里的表名——在该业务库上执行；
  SQL 执行历史、WDR 快照、活跃会话采样、会话与锁、等待事件这类实例级数据仍从 postgres 取。三条同时满足才带 dbName：登录时核实过中间件会切；
  脚本是业务库类；行方接口一里这条脚本声明了 dbName（行方没配好的不传，免得被拒）。
- **白名单按「读的是什么」重新划分执行库**：GaussDB 官方文档写明 STATEMENT_HISTORY「必须在 postgres 库内查询，其它库中不存数据」，
  WDR 快照、GS_ASP 也只存在 postgres 库。原先标为 appbusiness 的 52 条里，6 条读的正是这些数据（切过去就查不到），20 条读实例级视图（在哪执行都一样），
  本版都改回 postgres；另有 19 条读业务库对象却标成 postgres，改为 appbusiness。现在 46 条在业务库执行；脚本定义里的 `database_type` 是唯一依据，
  守卫测试逐条按读取对象核对。白名单清单标出每条的执行库。
- **登录核实是否真的切过去**：新探针 `login.current_db` 带 dbName 查 `current_database()`，回来的是用户给的库才写「**已直连**」；
  没切过去写「**未直连**」并说明原因（白名单没导本版增量、中间件不支持切库、库不存在或没有该库的连接权限），取数照旧走 postgres。
  切过去了但行方白名单里还有该切库的脚本没带 dbName 时，逐条列出。
- **只给实例、没给业务库登录时**，登录输出写明：会话、锁、慢 SQL / Top SQL、WDR 是整个实例的数据（所有库的都在里面），看这些不用指定业务库；表、索引、执行计划要看哪个业务库，登录时带 `--database`。测试环境实测原先模型会以为 Top SQL 只含 postgres 库的语句、建议「按业务库重新登录再看」。
- **回滚与混跑**：切到的业务库名单独存在会话旁边的 `<句柄>.route` 文件里，会话文件本身与 v1.4.10 格式相同——回滚到 v1.4.10、或按槽位替换期间新旧混跑，旧版照常读会话（当成不切库）。测试环境回滚实测：库名若写进会话文件，旧版读到不认识的键会让这个用户的所有取数技能报错。
- **部署自检**新增「业务库切换」「白名单切库标注」两项：本会话切过去没有；行方白名单里各脚本的执行库与本版是否一致。

### 改动

- **高危（行方报告 Bug 1 ~ 4）**：
  - **补全表名把函数里的 FROM 当成表**（Bug 1）：`EXTRACT(HOUR FROM 列)`、`TRIM(… FROM 列)`、`SUBSTRING(… FROM …)` 里的列被补成

    补上 `DELETE … USING`、`MERGE … USING`（M3）；补全后仍执行失败时自动用原 SQL 再试一次。
  - **SQL 审查把 `"a;b"` 这类引号标识符里的分号当语句结束**（Bug 2），与中间件侧切法不一致；现在一致。

  - **慢 SQL 被截成 5 条**（Bug 4，`--limit` 大于 20 或带 `--export` 时）：早期遗留的 `min(…, 5)`，展示条数改为由 `--limit` 决定，导出与报告一致。
- **中危**：`CREATE INDEX … USING btree/gin (…)` 解析失败致索引规则静默失效（M1）、函数索引的列取成函数名（M2）——列清单按括号配对解析、表达式整体保留；
  中间件返回小数形态的整数（`"3704.0"`）时时段健康检查等处报错（M4）——统一按容错方式转换；sqltune 加说明时重新构造异常的写法加保护（M5）；
  SKILL.md 写明中间件模式下 hypopg 验证不可用、索引建议标「未验证」（M6）。
- **受限账号下健康检查 Storage 整条失败**：只量执行账号有权限的库与表空间，没权限的写「无权限查看」。
- **平台运维账号的 SQL 不进业务榜单**：rdsAdmin、rdsBackup、rdsMetric、rdsRepl、rdsProxy 执行的 SQL（监控采样、备份等）从 Top SQL、慢 SQL、
  健康检查、WDR 的榜单里排除并写明条数；`GSDB_PLATFORM_ACCOUNTS` 可再加。现场 Top SQL 第一名就是 rdsAdmin 的 ASP 采样 SQL。
- **慢 SQL 脚本失败时有退路**：改用 Top SQL 脚本按平均耗时取、按阈值筛（没有开始时间筛选，报告写明）。现场有一台实例慢 SQL 脚本回 HTTP 400、

### 根规范模板替换

镜像里的 `/workspace/docs/` 预留了三份模板 `根规范-1.md`、`根规范-2.md`、`根规范-3.md`（第一行带 `ROOTSPEC-TEMPLATE` 标记）。
行内部署时换成正式规范，**每次升级用新版本的包再换一次**（新版本的镜像里又是模板）。

1. 准备一个目录，放正式规范：`.md` / `.txt` / `.docx` / `.pdf`。pdf 在下一步自动转成文字版 `.txt` 放进镜像（**扫描件没有文字层，要先转成 docx 或 md**）。
   Markdown 的一级标题、docx 的「标题 1」写规范名称，回答里的出处《…》按它写；没有时按文件名（pdf 按文件名，**文件名请写成规范名称**）。份数不限于三份，模板不用留。
2. 在跳板机上（架构与集群节点相同，docker 25 及以上），载入镜像**之前**对离线包执行：
   ```bash
   <离线包目录>/rootspec-overlay.sh --docs <规范目录>
   ```
   脚本给 runtime 与 kb-import 两个镜像各加一层，把模板换成你给的文件（**标签不变**，其余三个镜像原样），另出新包目录 `<离线包目录>-rootspec`，
   并刷新其中的 `release.yaml` 与各 sha256。原包不动。两种架构都要的，在两种架构的机器上各做一次。
3. 之后用新包：手工部署从《部署手册》阶段 1.2 接着做（`docker load` 新包目录里的镜像包）；用发版台的，把新包目录拷进发布包目录，并把原包目录挪走
   （同一版本只能有一份）。
4. 核对（载入后、推仓库前）：
   ```bash
   docker run --rm --entrypoint python3 gaussdb-agent-runtime:agent-v1.4.5-oc1.18.27 /workspace/search_docs.py --list
   ```
   列出的是你的规范，没有「（模板，未替换）」。kb-import 镜像同样核对。

同一批规范也照常**导入本行知识库**（知识库导入环境，与其他规范相同）：知识库可用时优先用知识库里的，镜像里的根规范是知识库不可用或查不到时的兜底。

### 新功能

- **固定池化**（可选的部署形态，取代 v1.2.0 的池化沙箱）：部署时固定 N 个 Pod、每个 Pod K 个槽位，运行中不建、不删、不补；

  满员时把闲置最久的在用者提前转保留、腾出的槽位留给等待的人，等待页每 30 秒自动重试。同 Pod 的人之间：各自的盘与进程空间、
  端口防冒充、腾挪即重启清盘。《固定池化手册》。
- **凭据不再进入模型所在的容器**：中间件令牌、SM2 签名私钥、模型 Key 由凭据代理在转发时加上——按需模式是用户 Pod 里的伴生容器，
  固定池化是 Pod 的管家。代理只往配置的中间件与模型地址转发、只转诊断接口，工号按本人强制写入。模型即使执行命令读环境变量，
  也读不到任何凭据。
- **opencode 工具权限真正执行**：原来写在 AGENTS.md 里的权限只是提示词，现在写进 opencode 的配置：不能联网、只能用 gaussdb-* 技能，
  命令行只放行技能脚本与几个只读命令（拒绝读环境变量、读 `/proc`、重定向写文件等）；诊断容器不能改文件，知识库导入容器可以（写草稿）。
- **回答模板化**：健康检查、故障排查、SQL 优化、知识问答、WDR 解读、Top SQL / 慢 SQL 榜单各有固定版式，共用开头（总体状态 → 短结论）
  与结尾（「需要就 xxx 展开说明吗？」）；正文每段先「应用视角」（给开发人员）、再「数据库机制」（给数据库工程师）。
  SQL 优化增加现状与趋势（执行次数、平均 / 最大耗时、近 7 天按小时的变化、哪个时间点突然变慢、当时执行计划变没变）与改写前后对比；
  WDR 报告重排为负载画像 → 问题与元凶 → 解决方案 → 总结和结论 → 附录。测试环境前后对比：版式检查从 7/62 项到 52/52 项。

  被锁挡住的语句不再占满榜首。
- 大盘：报告文件取不到时（索引里还登记着）退回离它最近的同类报告并写明，不再整页「HTTP 404」；下次存档自动清掉失效的索引条目。
- 固定池化：保留期间 NAS 上的数据丢了（误删、恢复不全），回来时用槽位里的保留副本恢复并写回，不再判过期把唯一的副本清掉。

### 新功能

- **时段锁回溯**（`gaussdb-lockwait --from … --to …`）：从数据库自带的活跃会话采样（ASP）事后还原某段时间里谁挡了谁——阻塞对、阻塞链与根、根会话的状态 / 应用 / 事务开始时间、约等了多久（采到次数 × 约 10 秒，估算）。事后回看不生成 kill 语句。时段体检终点在过去时，「锁与阻塞链」不再是「回看不了」，改由它填。
- **历史真实执行计划**：按 sql_id 看执行计划时，语句文本带占位符（无法重新 EXPLAIN）或被截断，先给语句历史里记下的当时真实执行的计划（带实际耗时与行数），标明是哪次执行。
- **WDR 附录带真实计划**：WDR 采集时取根因语句在窗口内的真实执行计划，附录直接展示，不再写「本次未取到」。
- **部署手册 §0.4 / 对接清单 §5**：写明事后分析能回看多久取决于哪些数据库参数（语句历史、活跃会话采样、WDR 快照的保留期），由 DBA 评估开启。

### 修复

- sqltune / explain：`schema_name` 是搜索路径串（如 `fl, public`）时按逗号拆开逐段校验并整串切换，不再报「不是合法标识符、未切换 search_path」。
- explain：文本是归一化的时，报错不再一律说「statement_history 里没有这条」。
- 大盘：时段体检「深挖」首句的评估窗口带秒。原来只到分钟，深挖时起点退到上一个快照，窗口变宽、平均活跃会话被摊薄，和卡片上的数对不上。

### 升级前先看

### 新功能

- **时间段的 Top SQL 与健康检查**：「最近 30 分钟」「10:46 到 11:07」都能问。取包住这段时间的 WDR 快照 / 自留采样 / 此刻两端相减——不追求精确、只保证覆盖住，并写明要的是哪段、实际评估的是哪段、为什么；跨过实例重启时只覆盖重启之后那段。时段体检里连接、锁、膨胀等瞬时状态逐项写明「回看不了」；终点是此刻时给当前值并标明。
- **死锁日志解析**（`gaussdb-lockwait --deadlock-log -`）：用户把日志里 `deadlock detected` 那几段贴进对话，解析出环、语句、牺牲者，按模式给出改法。不依赖日志前缀，不连库。WDR 与健康检查报死锁次数时会引导用户贴日志。
- **新技能 `gaussdb-config`（参数体检）**：只报客观错误——参数自相矛盾、会静默丢数据的危险配置、按实例内存预算算出的超卖；不给凭空的推荐值。
- **健康检查补六项**：冻结水位、占用量、同步提交与部署形态、WAL 复制槽、线程池用量、分区数。**膨胀估算**（空间比应占多了多少）。
- **WDR**：各维度元凶从耗时前 200 条里找，榜外冠军另列；临时溢出写明能归到语句的占多少、冠军是哪条（带 sql_id，后续调优直接用）；点 sql_id 看全文与执行计划；报告给出确定性的「下一步」。
- **大盘显示时段报告**：对话里给的链接直接打开那一份时段榜 / 时段体检；按评估窗口筛选；深挖首句带评估窗口。

### 修复

- **WDR 的 DB time 少报约 8800 倍、Top SQL 漏掉窗口内新出现的语句**；文件 IO / 缓存 / 库统计同样的内连接漏行（文件 IO 实测 1468 个文件只统计到 185 个）。
- **空闲库被判告警**：每小时 DB time 零点几秒的窗口里「LWLOCK 占 DB time 171.8%」被判 🟠。现在空闲窗口不判比例；等待占比与 DB time 自相矛盾时明说不可信、不判告警。
- **Top SQL**：同一语句按执行用户拆成多行时重复上榜、增量算错；SQL 开头的注释占满显示宽度；「最近 10 分钟」原来会阻塞 10 分钟（现在回看已有的采样 / 快照，不阻塞）。
- **sql_id 查不到**：说清原因（实例何时重启），语句在 WDR 存档里有文本时直接给出并指路出计划。
- **对话里的大盘链接点不开**（原来给的是裸路径）；报告里不再出现让模型照抄的命令行。
- 健康检查在单机库上把「同步提交」误报为风险；冻结水位误写为「会停写」（本内核是 64 位事务号）。
- 参数体检不再拿 `reset_val` 判「改了未生效」（本内核上 108 个参数的 `reset_val` 没有有效值）。

### 修复

- **第二次打开大盘整页空白。** 网关给没有消息体的响应（304 / 204 / HEAD）也加了分块编码，浏览器复用连接时把多出来的字节当成下一个响应，一个模块坏掉整页就空白。模拟 SSO 工具（`k8s/tools/sso-sim.py`）同样修了。
- **新工号首次登录，用户容器反复重启。** 个人目录被自动建成 root 属主、容器写不进。现在由初始化容器以 uid 1000 建好并确认可写；建不了时把原因与修复命令写进容器状态。
- **用户容器起不来时，用户等满 120 秒只看到「正在启动」，网关日志里没有原因。** 现在网关读 Pod 状态与事件，归成一类原因：拉不到镜像、容器配置缺失、个人目录初始化失败、NAS 挂不上、调度不上。前三类等下去也不会好，网关不再等满超时，当场回 503；网关日志写完整原因，给用户只说是哪一类。
- **写进 `agent-roles` 的知识库管理员不生效。** 网关现在读这张表（30 秒内生效），与角色头两者满足一个即可。
- **管理员进不了知识库导入容器。** 网关以前只转发到诊断容器。现在访问 `/kb-import/` 切到导入容器、`/runtime/` 切回；也可由 SSO 给管理员入口加请求头 `X-Agent-Target: kb-import`（接入手册 §2.5）。
- **中间件模式下库名写错不报错。** 库名不发给中间件，写错只会变成报告抬头上的错误标签。现在登录时核对，不一致就不登录，并告诉用户实际的库名。
- **镜像放在内网仓库时，用户一登录就 504。** 网关新增 `USER_IMAGE_REGISTRY`（用户容器镜像的仓库前缀）。
- **`delete` 回收模式会把这个人的平台令牌一起删掉。** 管理员的导入容器一闲置，正在用的诊断容器与 `grmp-token-<工号>` 跟着被删，下次登录报「尚未开通」。现在只删闲置的那一个容器。
- **用户容器在对话进行中被删除时，网关把那条连接写坏。** 现在干净地结束。

### 新功能

- **大盘两种风格**：普通（运维舱）与文艺（「GaussDB智能体日报」），页面顶部滑块切换，选择记在浏览器里。
- **从对话直达大盘**：健康检查、Top SQL、WDR 跑完后，智能体在回答末尾给出这一份报告在大盘上的链接。
- **大盘按时间段筛选**已经跑过的报告（顶栏「时间段」）。WDR 按快照窗口算。
