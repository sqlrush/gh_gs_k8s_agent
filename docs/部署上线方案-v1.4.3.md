## 1. 方案概述

### 1.1 系统组成

| 组件 | 镜像 / 来源 | 形态 | 作用 |
|---|---|---|---|
| 接入网关 | `gaussdb-agent-gateway` | Deployment，2 副本 | 认工号（统一认证加的请求头 + 信任凭据）、按工号分配用户环境、反向代理对话与报告；运维接口 `/admin/*` |
| 用户环境 | `gaussdb-agent-runtime` | 每人一个 Pod（按需），或固定池化的槽位 | opencode 1.18.27 + 17 个诊断技能 + 知识库只读查询；每个 Pod 带一个凭据代理容器 |
| 标准知识库 | `gaussdb-agent-kbstd`（我方发布，不从源码构建） | 部署时跑一次的 Job，装完退出 | GaussDB 官方文档集（25.1.32 集中式，6023 条，含检索索引），自动装进 NAS 的 `kb/docsets/` |
| 知识库导入环境 | `gaussdb-agent-kb-import` | 每个知识库管理员一个 | 知识库导入、入库前标准化、官方文档集（CHM）导入；内网网页剪藏的接收（4095，只有网关能到） |
| 前端（大盘与对话页） | 前端方自建 | 部署进本集群或贵方门户 | 按《前端对接接口说明》接入 |
| NAS | 贵方存储 | 一个 RWX 卷 | 唯一的状态所在：`users/<工号>/`（会话、报告）、`kb/`（知识库与索引） |
| 统一认证（SSO） | 贵方 | 反向代理 / 网关 / WAF | 认人，把工号与信任凭据加进请求头 |
| 中间件（GRMP） | 贵方 | 已有系统 | 按白名单执行只读诊断脚本，按人令牌鉴权，可选 SM2 签名 |
| 模型服务 | 贵方 | OpenAI 兼容接口 | 推理；可选 embedding 端点给知识库用 |

### 1.2 请求链路

- **对话**：浏览器 → 贵方统一认证（认人，加工号头与信任凭据）→ 接入网关（核对信任凭据，找到或创建这个工号的用户环境）→ 用户环境里的 opencode。
- **诊断取数**：opencode 里的技能 → 同 Pod 的凭据代理（加上本人中间件令牌、SM2 签名、工号）→ 贵方中间件 → 被诊断的数据库。技能只能调用白名单里登记过的只读脚本。
- **推理**：opencode → 凭据代理（加上模型 Key）→ 贵方模型服务。
- **报告与大盘**：技能把报告写进本人 NAS 目录；前端经网关的 `/reports/*` 读取，大盘页面走 `/dash/*`。
- **知识库**：管理员在导入环境里导入规范、案例、官方文档，写进 NAS 的 `kb/`；所有用户环境只读这份知识库。
- **网页剪藏**（可选）：知识库管理员在**已登录**的内网网页上点书签「导入知识库」→ 网关提供的剪藏页（只收 `KB_CLIP_ORIGINS` 里网站交来的内容）→ 本人导入环境的剪藏接收 → 知识库收件目录，并自动新开会话导入。页面内容只经管理员的浏览器进来，**导入环境不访问任何内网网站**。

### 1.3 两种运行形态

| | 按需模式（默认） | 固定池化（可选） |
|---|---|---|
| 怎么运行 | 工号第一次登录时现建一个 Pod，闲置 30 分钟后收起 | 部署时固定 N 个 Pod × 每个 K 个槽位，运行中不建、不删、不补 |
| 首次进入 | 约 8 秒（现建 Pod） | 1–2 秒（分配槽位、载入历史） |
| 离开后回来 | 闲置收起后再来要重新建 Pod | 0–1 秒（粘性保留：人走了槽位先不还） |
| 满员 | 不存在满员，受集群资源约束 | 等待页每 30 秒自动重试，并提前请闲置的人让位 |
| 资源 | 按实际在线人数占用 | 按池子规模固定预留 |
| 适用 | 使用人数不多、登录分散 | 大量用户集中登录（如版本上线后的业务高峰） |

**建议**：先以按需模式上线、跑通全部验收；预计同时在线超过约 50 人、或要求秒级进入时，再按第 11 章切到固定池化。两种模式的 NAS 布局完全相同，可以来回切换，数据不迁移。

### 1.4 安全设计要点

- **凭据不进模型所在的容器**：中间件令牌（按人）、SM2 签名私钥、模型 Key 只注入凭据代理容器，由它在转发时加上；模型执行命令读环境变量也读不到。
  代理只往配置好的中间件与模型地址转发、只转发诊断接口，工号强制写成本人。
- **只读白名单**：技能只能按名字调用中间件里预先登记的脚本，128 条全部是只读查询，只访问系统视图与系统表，不读业务数据，不含 DML / DDL。
- **网关不信任请求头**：只认带着信任凭据的请求，信任凭据没配就拒绝启动；不带凭据的请求一律 403。
- **网络策略白名单**：用户容器只能出到中间件、模型服务与 DNS，访问不到网关、k8s API 与集群里的其他服务；网关只能访问 k8s API、用户容器与前端。
- **最小权限**：全部容器以非 root（uid 1000）运行；opencode 的工具权限写进配置真正执行：不能联网，只能用诊断技能，命令行只放行技能脚本与少数只读命令。
- **固定池化的同 Pod 隔离**：每个槽位独立的系统身份、进程空间与盘，凭据只在管家容器里，换人时容器重启清盘并经外部核验。

### 1.5 本版本要点

**v1.4.3（本版）**：**存储过程源码的 ADM_SOURCE 兜底**——开了对象隔离（`ENABLE PRIVATE OBJECT`）的库，执行账号查 pg_proc 受行级访问控制、联表 0 行，存储过程诊断与调优以前只能给出「过程未找到」的排查报告；现在接着按 ADM_SOURCE 取源码，包内过程从包体里切出来，报告写明取自包体第几行并附包级声明。白名单新增 2 条（共 128 条）；ADM_SOURCE 默认只有系统管理员能读，执行账号要不要授权由贵方 DBA 决定（第 14.1 节第 4 步）。Secret、agent-config、网络策略不变。

**v1.4.2**：**GaussDB 官方文档集随部署自动装上**——作为标准知识库发布在镜像 `gaussdb-agent-kbstd` 里，`kubectl apply` 后一次性 Job 把它装进知识库（逐文件核对、同版本跳过、不碰贵方自己的知识、不要任何网络），不再需要管理员从 CHM 导一遍。白名单、中间件、Secret、agent-config 都不变。

**v1.4.1**：只改知识库导入，白名单、中间件、Secret 都不变。

- **内网网页导入知识库（网页剪藏）**：需要登录的 Wiki / Confluence / 门户页面，由知识库管理员在已登录的浏览器里点书签剪藏；
  模型按现有流程整理（故障记录按六要素成案例、规范条款化、手册 / 缺陷 / 基线 / Wiki 按八类模板），筛掉导航、评论与无关段落，
  写入前给管理员确认清单；原始网页挂成 L3 证据，出处追得到原网页。第一次用时由模型一步一步带着装书签；
  书签用不了时浏览器另存为 .mhtml 拖进剪藏页。允许剪藏的网站在 `agent-config` 的 `KB_CLIP_ORIGINS` 里配，空 = 关闭。
- **扫描件 PDF 看图转录**：每页渲染成图片由模型逐页转录（看不清的标出来问管理员，不猜），以前直接拒绝。
- **PPT（.pptx）导入**：每页的标题、要点、表格、备注与幻灯片里的图片。

**v1.4.0 起已有**：

- **固定池化**（可选部署形态）与**凭据代理**（凭据不进模型容器）。
- **回答模板化**：健康检查、故障排查、SQL 优化、知识问答、WDR 解读、Top SQL / 慢 SQL 各有固定版式，兼顾开发人员与数据库工程师两种读者；
  出自知识库的句子上色并注明出处（贵方知识蓝色 `#2f6fdb`，产品文档青色 `#0f7c86`）。
- **知识库**：八类知识类型、L0–L3 渐进式披露、按环境画像判断适用性、官方文档集（CHM）导入。
- **取数修正**：用演练库造出 34 类典型故障、两轮逐项核对后修正的健康检查、锁回看、内存分析、Top SQL、SQL 调优等问题。
- **中间件接口路径前缀改为部署配置**：`agent-config` 的 `GRMP_PATH_PREFIX`，必填。
- 诊断脚本白名单 v1.4.0 时为 126 条（相对 v1.3.x 的 123 条：更新 12 条、新增 3 条）；v1.4.3 新增 2 条，共 **128 条**。

### 2.2 环境要求

**构建机**（Linux x86_64 / ARM，或 macOS）：Docker 20.10 以上（带 buildx）、git、curl、磁盘剩余 20 GB 以上。构建时要访问
`github.com`（代码、opencode 二进制）、Docker Hub（基础镜像 `python:3.12-slim-bookworm`）、`deb.debian.org`、`pypi.org` / `files.pythonhosted.org`、`models.dev`。
构建机不能上外网时，见第 5.3 节离线方式。

**Kubernetes 集群**：

| 要求 | 说明 |
|---|---|
| Kubernetes 1.24 以上 | 实测过 1.36 |
| 网络插件支持 NetworkPolicy | Calico / Cilium 等。不支持时策略不报错但不生效，第 8.6 节有验证方法 |
| 一个 RWX 存储 | NFS，或已有的 RWX StorageClass |
| 节点能拉镜像仓库 | 私有仓库配 `imagePullSecrets` 或节点级凭据；节点架构与镜像架构一致（可同时构建两种架构） |
| 跳板机 | 装 `kubectl`，有 `gaussdb-agent` 命名空间的管理权限；固定池化渲染要 Python 3.8+ |

**资源估算**：

| 部分 | 预留（request） | 上限（limit） |
|---|---|---|
| 网关 ×2 | 每个 0.1 核 / 128 MiB | 每个 1 核 / 512 MiB |
| 按需模式：每个在线用户 | 约 0.27 核 / 560 MiB（opencode 0.25 核 / 512 MiB + 凭据代理） | opencode 2 核 / 2 GiB |
| 固定池化：每个槽位 | 0.1 核 / 768 MiB | 2 核 / 2 GiB |
| 固定池化：每个 Pod 的管家 | 0.05 核 / 64 MiB | 1 核 / 512 MiB |

单人实测：空闲 350–500 MiB；一次 WDR 分析峰值约 0.7 GiB、CPU 平均 0.3 核、峰值 0.9 核。按「同时在线人数 × 0.9 GiB、× 0.5 核，再留 30%」配节点；
固定池化默认规模 16 个 Pod × 8 个槽位（128 人）预留约 13.6 核 / 97 GiB。**上线前在贵方环境装 metrics-server 复测。**
NAS 容量：每人的会话与报告一般在几十 MB 以内，知识库视导入量而定（官方文档集约数百 MB），建议起步 500 GiB。

**出网**（网络策略里要放行的地址）：

| 从 | 到 | 端口 |
|---|---|---|
| 网关 | k8s apiserver 的真实地址（`kubectl -n default get endpoints kubernetes`） | 443 / 6443 |
| 用户环境、知识库导入环境 | 中间件 | 中间件端口 |
| 用户环境、知识库导入环境 | 模型服务（公网时 `0.0.0.0/0`，或经 HTTPS 代理） | 443 / 80 |
| 全部 | 集群 DNS | 53 |

集群内的放行（网关 → 用户环境 4096 / 4097、网关 → 知识库导入环境 4095 / 4096）清单里已经写好，不用改。网页剪藏**不需要**给导入环境开任何内网出网。

## 4. 拉代码

```bash
git clone https://github.com/sqlrush/gh_gs_k8s_agent.git
cd gh_gs_k8s_agent
git checkout agent-v1.4.3
git describe --tags          # 应输出 agent-v1.4.3
TAG=agent-v1.4.3-oc1.18.27
```

**之后所有命令都在这个目录里执行。** `oc1.18.27` 是镜像里的 opencode 版本。内网有代码托管时，可以把本仓库连同标签镜像到内网再拉。
各目录的作用见《代码结构说明》。对应《完整手册》第 2 章。

## 5. 构建镜像

### 5.2 方式 B：两种架构一次构建并直接推进仓库（正式发布推荐）

### 5.3 方式 C：构建机不能上外网（离线包）

在一台能上网的机器上构建两种架构并打离线包，带进内网：

```bash

bash scripts/package-images.sh "$TAG"                                    # → dist/gaussdb-agent-v1.4.3-oc1.18.27/
```

离线包里是两种架构的镜像 tar.gz（各带 sha256）、k8s 清单与文档。内网里：

```bash
sha256sum -c *.sha256
gunzip -c gaussdb-agent-v1.4.3-oc1.18.27-<架构>.tar.gz | docker load
```

x86（amd64）包里的镜像标签带 `-amd64` 后缀，推之前先去掉（鲲鹏 arm64 包没有后缀，跳过这一步）：

```bash
for img in runtime kb-import gateway kbstd; do docker tag gaussdb-agent-$img:$TAG-amd64 gaussdb-agent-$img:$TAG; done
```

再按第 6 章推进内网仓库。

## 7. 中间件导入诊断脚本白名单（中间件团队）

用户环境里的技能只能按名字调用中间件里预先登记的脚本。**白名单里没有的脚本，对应功能用不了**（报「未注册脚本」或「脚本不存在」）。
全部 128 条都是只读查询，只访问系统视图与系统表，不读业务数据，不含 DML / DDL。文件都在本仓库 `docs/delivery/`：

| 情况 | 导哪份 | 结果 |
|---|---|---|
| **第一次部署** | `scripts.sql`（全量） | 128 条 |
| 已导入 126 条（v1.4.0 ~ v1.4.2） | `scripts-delta-20261030.sql`（新增 2 条：存储过程源码的 ADM_SOURCE 兜底） | 128 条 |
| 已导入 123 条（v1.3.1 / v1.3.2） | 先 `scripts-delta-20261024.sql`（更新 12 条），再 `scripts-delta-20261026.sql`（新增 3 条），最后 `scripts-delta-20261030.sql`（新增 2 条） | 128 条 |
| 已导入 118 条（v1.3.0） | 先 `scripts-delta-20261022.sql`（新增 5 条），再上面三份 | 128 条 |
| 已导入 105 条（v1.2.0 及更早） | 依次 `scripts-delta-20261018.sql`（新增 13、更新 9）→ 20261022 → 20261024 → 20261026 → 20261030 | 128 条 |

导入前确认两处与贵方规范对齐：`create_user` / `last_modify_user` 当前填 `'999999999'`，要求真实工号时统一替换；
`id` 用 `grmp.script_config_seq.nextval`，不硬编码。

**导入后自检**：

```sql
SELECT count(*) FROM grmp.script_config WHERE scene = 'AGENT';                              -- 应为 128
SELECT count(*) FROM grmp.script_config
 WHERE script_name IN ('procinfo.source_adm', 'proctune.source_adm');                       -- 应为 2
```

升级导了 `scripts-delta-20261024.sql` 的，再执行文件末尾「导入后自检」一节的 md5 核对语句，应返回 0 行。
每条脚本的用途、参数与 SQL 全文见附录 A 与《诊断脚本白名单清单》（`docs/delivery/白名单脚本清单.md`）。

没导 20261026 那 3 条时其余功能不受影响，只是 SQL 优化回答的第一段写「现状数据暂不可得」。没导 20261030 那 2 条时，pg_proc 取得到源码的存储过程照常分析，只是对象隔离下取不到源码时报告写「中间件里还没有登记这条脚本」。

## 8. 部署到 Kubernetes（平台团队）

在跳板机的仓库目录里执行，先定义与构建时相同的 `REG`、`TAG`。

### 8.1 清单指向镜像仓库

```bash
sed -i "s#image: gaussdb-agent-gateway:.*#image: $REG/gaussdb-agent-gateway:$TAG#" k8s/base/gateway.yaml
sed -i "s#image: gaussdb-agent-kbstd:.*#image: $REG/gaussdb-agent-kbstd:$TAG#" k8s/base/kbstd-install.yaml
sed -i "s#image: gaussdb-agent-kb-import:.*#image: $REG/gaussdb-agent-kb-import:$TAG#" k8s/base/kbstd-install.yaml
sed -i "s#  USER_IMAGE_REGISTRY: .*#  USER_IMAGE_REGISTRY: \"$REG\"#; s#  USER_IMAGE_TAG: .*#  USER_IMAGE_TAG: \"$TAG\"#" k8s/base/configmap-gateway.yaml
grep -rn "image:\|USER_IMAGE_REGISTRY:\|USER_IMAGE_TAG:" k8s/base/ | grep -v ":\s*#" | grep -v example
```

应看到 5 行（含标准知识库安装 Job 的两处），地址都以 `REG` 开头、版本都是 `TAG`。**`USER_IMAGE_REGISTRY` 必须填**：用户容器的镜像由网关按它现拼，留空时节点会去 Docker Hub 拉、用户一登录就卡住。
**网关与用户镜像必须同一版本**（用户 Pod 里的凭据代理跑的是用户镜像里的程序）。macOS 上 `sed -i` 写成 `sed -i ''`。对应《完整手册》5.1。

### 8.2 接上存储

集群已有 RWX StorageClass：把 `k8s/base/nas-pvc.yaml` 的 `storageClassName` 改成它。用 NFS：

```bash
cp k8s/base/nas-pv-nfs.example.yaml k8s/base/nas-pv-nfs.yaml
vi k8s/base/nas-pv-nfs.yaml                  # 只改最后两行:server 与 path
kubectl apply -f k8s/base/nas-pv-nfs.yaml
```

存储管理员在导出目录下先建好三个目录，属主 1000：

```bash
mkdir -p <导出路径>/users <导出路径>/admins <导出路径>/kb && chown -R 1000:1000 <导出路径>
```

对应《完整手册》5.2。

### 8.3 创建基础资源

```bash
kubectl apply -k k8s/base
kubectl -n gaussdb-agent get pvc,pods
```

PVC `nas` 应为 `Bound`。两个 `gateway` Pod 此时 `CrashLoopBackOff` 属正常（还没建信任凭据，网关按设计拒绝启动）；
`ImagePullBackOff` 是节点拉不到镜像。同时建了一次性 Job `kbstd-install-v1-4-3`，它的 Pod 变成 `Completed` 即官方文档集已装进知识库（第 12 章第 5 步）；
NAS 还没接好时它会失败重试，接好后自己就过。对应《完整手册》5.3、5.7。

### 8.4 三个 Secret

```bash
read -rs -p "模型服务 key: " V && echo
kubectl -n gaussdb-agent create secret generic model-api --from-literal=MODEL_API_KEY="$V"; unset V

TRUST=$(openssl rand -hex 24); ADMIN=$(openssl rand -hex 24)
kubectl -n gaussdb-agent create secret generic gateway-auth --from-literal=TRUST_SECRET="$TRUST" --from-literal=ADMIN_TOKEN="$ADMIN"
printf '%s' "$TRUST" > ~/.agent-trust && printf '%s' "$ADMIN" > ~/.agent-admin && chmod 600 ~/.agent-trust ~/.agent-admin
unset TRUST ADMIN

# 中间件要求 SM2 签名时才需要:
read -rs -p "SM2 私钥: " V && echo
kubectl -n gaussdb-agent create secret generic grmp-sm2 --from-literal=GRMP_SM2_PRIVATE_KEY="$V"; unset V
```

`TRUST_SECRET` 要同时交给统一认证团队（转发时放进信任凭据头），**两处保持一致，按贵方密钥管理规范保管**；
`ADMIN_TOKEN` 只给运维用。对应《完整手册》5.4。

### 8.5 填 agent-config

```bash
kubectl -n gaussdb-agent patch configmap agent-config --type merge -p '{"data":{
  "GRMP_API_HOST":"<中间件IP>","GRMP_API_PORT":"<中间件端口>","GRMP_PATH_PREFIX":"<中间件接口路径前缀>",
  "MODEL_BASE_URL":"<模型服务地址,以 /v1 结尾>","MODEL_ID":"<模型名>","MODEL_PROVIDER_NAME":"<显示名>"}}'
# 中间件要求签名时:
kubectl -n gaussdb-agent patch configmap agent-config --type merge -p '{"data":{"GRMP_APPKEY":"<中间件给的 Appkey>"}}'
```

- **`GRMP_PATH_PREFIX` 必填**：技能调用中间件的两个接口是 `<前缀>/common-operations` 与 `<前缀>/common-operations/invoke`。以 `/` 开头、只写路径、末尾不带 `/`。
  没填时登录数据库报「中间件接口路径前缀没有配置」；填错时中间件回 404。
- 中间件地址不能写 `localhost` / `127.0.0.1`（在容器里指容器自己）。
- （可选）网页剪藏：`"KB_CLIP_ORIGINS":"https://wiki.<内网域名>,https://confluence.<内网域名>"`——允许剪藏的内网网站，每项只写「协议://主机[:端口]」，
  不带路径；空 = 关闭。网关与导入环境读的是这同一份，改完重启网关。写错格式网关拒绝启动并在日志里指出是哪一项。
- 签名口径、实例别名、模型看图、大盘站点前缀等其余配置项见附录 B。改了配置之后，**之后创建 / 重启的**用户容器才读到新值。

对应《完整手册》5.5。

### 8.6 出网策略按实际地址改

清单里的出网地址段是占位值，要改 4 处：

```bash
kubectl -n default get endpoints kubernetes          # 查 apiserver 的真实地址
APISERVER=<上面查到的 IP>
GRMP_IP=<中间件IP>; GRMP_PORT=<中间件端口>
MODEL_CIDR=0.0.0.0/0                                 # 模型服务在内网且地址固定时换成它的地址段
kubectl -n gaussdb-agent patch networkpolicy gateway-policy --type json -p "[{\"op\":\"add\",\"path\":\"/spec/egress/3/to/-\",\"value\":{\"ipBlock\":{\"cidr\":\"$APISERVER/32\"}}}]"
kubectl -n gaussdb-agent patch networkpolicy runtime-policy --type json -p "[{\"op\":\"replace\",\"path\":\"/spec/egress/1\",\"value\":{\"to\":[{\"ipBlock\":{\"cidr\":\"$GRMP_IP/32\"}}],\"ports\":[{\"port\":$GRMP_PORT,\"protocol\":\"TCP\"}]}},{\"op\":\"replace\",\"path\":\"/spec/egress/2/to\",\"value\":[{\"ipBlock\":{\"cidr\":\"$MODEL_CIDR\"}}]}]"
kubectl -n gaussdb-agent patch networkpolicy kb-import-policy --type json -p "[{\"op\":\"replace\",\"path\":\"/spec/egress/1/to\",\"value\":[{\"ipBlock\":{\"cidr\":\"$MODEL_CIDR\"}}]}]"
```

多 master 的集群每个 apiserver 地址都要放行。出网要经 HTTPS 代理的，开通工号后用 `runtime-doctor.sh <工号> --fix --proxy <代理IP:端口>`。
**一定要实测策略在生效**（网络插件不支持时策略不报错、只是不生效）：按《完整手册》5.6 起两个临时 Pod，带用户容器标签的那个访问网关必须不通（`000`）。

### 8.7 启动网关

```bash
kubectl -n gaussdb-agent rollout restart deploy/gateway
kubectl -n gaussdb-agent rollout status deploy/gateway --timeout=180s
kubectl -n gaussdb-agent logs -l app=agent-gateway --tail=2
```

最后一行形如：`网关就绪:0.0.0.0:8080 · 命名空间 gaussdb-agent · 用户镜像标签 agent-v1.4.3-oc1.18.27 · 诊断容器 按需建 · …· 信任来源 共享密钥 · 控制 API 已启用`。
两个 `gateway` 都是 `1/1 Running`。对应《完整手册》5.8。

## 11. （可选）固定池化

前提：按需模式已跑通第 10 章。

```bash
# ① 控制密钥(网关与各 Pod 的管家共用)
kubectl -n gaussdb-agent create secret generic sandbox-control --from-literal=KEY="$(openssl rand -hex 32)"
# ② 渲染并部署池子(默认 16 个 Pod × 8 个槽位)
python3 k8s/tools/render-pool.py --image $REG/gaussdb-agent-runtime:$TAG \
    --pool-size 16 --slots-per-pod 8 \
    --grmp-cidr $GRMP_IP/32 --grmp-port $GRMP_PORT --model-cidr $MODEL_CIDR --model-ports 443 > pool.yaml
kubectl apply -f pool.yaml
kubectl -n gaussdb-agent get pods -l app=gaussdb-agent,role=pool          # 每个 9/9 Running
# ③ 网关切到固定池化
kubectl -n gaussdb-agent patch configmap gateway-config --type merge -p '{"data":{"RUNTIME_MODE":"pool"}}'
kubectl -n gaussdb-agent rollout restart deploy/gateway
# ④ 从按需模式切过来时,把按需的用户容器缩到 0(容器退出前把数据写回 NAS)
kubectl -n gaussdb-agent scale deploy -l role=runtime --replicas=0
```

- 规模：`--pool-size` 1–64、`--slots-per-pod` 1–16，单池最多 1024 个槽位；资源按第 2.2 节估。
- 池化参数（闲置转保留 30 分钟、保留 7 天、每 Pod 留 1 个空槽位、满员时提前转保留闲置 10 分钟以上的人等）在 `gateway-config`，见附录 B。
- 验证：`curl -s -H "X-Admin-Token: $(cat ~/.agent-admin)" http://127.0.0.1:18089/admin/pool` 看每个 Pod 与槽位的状态。
- 切回按需：`kubectl delete -f pool.yaml`，`RUNTIME_MODE` 改回 `ondemand`，重启网关。数据都在 NAS，不丢。
- 集群有 gVisor / Kata 时，渲染加 `--runtime-class <名字>` 整池启用沙箱运行时。

对应《完整手册》5.12（含渲染参数全表）。

## 12. 知识库初始化（知识库管理员）

1. **开通管理员**：统一认证传的角色含 `kb-admin`（`gateway-config` 的 `KB_ADMIN_ROLES` 可改），或把工号登记进 ConfigMap `agent-roles` 的 `kb-admins`。
   管理员访问 `/kb-import` 即进入自己的导入环境（模拟 SSO 下在命令末尾加参数 `kb-admin`）。
2. **建索引**：没有向量库要初始化，索引是 NAS 上的 `kb/index/store.sqlite`，导入流程会自动建；要手工建一次：
   `kubectl -n gaussdb-agent exec deploy/kb-import-<管理员工号> -c opencode -- sh -c '. /data/env.sh && python3 /opt/agent/config/opencode/skills/gaussdb-kb-import/scripts/kb.py index'`
3. **导入贵方知识**：在导入环境里把规范、案例（工单）、手册交给模型，按提示确认类型（八类：规范、案例、环境画像、指标基线、已知缺陷、处置手册、产品文档、Wiki）；
   文件放进 NAS 的 `kb/inbox/uploads/`（或 `kubectl cp` 进导入容器的 `/nas/kb/inbox/uploads/`）。
   扫描件 PDF 由模型逐页看图转录、PPT（.pptx）按页抽取，都要模型服务支持图片输入（`MODEL_INPUT_MODALITIES` 含 `image`）；老格式 `.ppt` / `.xls` / `.rtf` 先另存为新格式。
4. **登记环境画像**（建议）：`kb.py profile --system <系统代号> --alias <连接别名> --version-string "<登录输出里的版本串>"`，补全后 `kb.py add`。
   画像只写连接别名，不写 IP、主机名与口令。诊断时据此判断知识条目适不适用本实例。
5. **官方文档集（部署时已自动装上）**：GaussDB 官方文档集（G25132C，25.1.32 集中式，6023 条）由第 8.3 节 `apply -k` 建的一次性 Job `kbstd-install-v1-4-3` 装进 `kb/docsets/`，不用再从 CHM 导入。核对：`kubectl -n gaussdb-agent logs job/kbstd-install-v1-4-3` 是 `[installed] G25132C 已装上 … 6023 条`；`ImagePullBackOff` 是没推标准知识库镜像或 8.1 没改到 `kbstd-install.yaml`；权限错误是 NAS 的 `kb/` 不是 uid 1000 可写，改好后 `kubectl -n gaussdb-agent delete job kbstd-install-v1-4-3 && kubectl apply -f k8s/base/kbstd-install.yaml`。换别的版本的官方文档仍可让模型按「官方文档集」流程导入。
6. **从旧版本升级的知识库**：跑一次 `kb.py migrate` → 确认清单 → `kb.py migrate --apply` → `kb.py validate && kb.py index`。不迁移也能用，没类型的条目显示「未分类」。
7. **（可选）embedding**：知识库配置里接上 embedding 端点后再跑一次 `kb.py index` 就补齐向量；不配时检索走词法 + 图，不影响使用。
   embedding 服务在集群外时，网络策略要放行（固定池化渲染用 `--egress <地址>/32:<端口>`）。
8. **（可选）内网网页导入**：`agent-config` 配好 `KB_CLIP_ORIGINS`（第 8.5 节）后，管理员在导入环境里说「导入这个网页 <链接>」，
   模型会先核对剪藏开没开、网站在不在名单，再一步一步带着装书签（安装页 `/kb-import/clip/install`）；之后在已登录的页面上点书签「导入知识库」，
   核对标题与字数后点「导入」，剪藏页自动在导入环境里新开会话整理。书签用不了时：浏览器「另存为 → 网页，单个文件（.mhtml）」，拖进剪藏页 `/kb-import/clip`。
   不要把内网系统的 cookie、口令发给模型。

完成标志：`kb.py health` 状态行正常、八类知识有计数；对话里问一条已导入的规范能引用到，并上色注明出处。对应《完整手册》5.7、5.11。

## 16. 运维要点

| 事项 | 做法 |
|---|---|
| 某个人用不了 | `bash k8s/tools/runtime-doctor.sh <工号>`，按「诊断意见」执行；`--fix` 修目录属主与代理 |
| 看网关日志 | `kubectl -n gaussdb-agent logs -l app=agent-gateway --tail=200` |
| 看某人的容器 | `kubectl -n gaussdb-agent logs deploy/runtime-<工号> -c opencode`（凭据代理是 `-c credproxy`） |
| 用户容器的回收 | 按需模式闲置 30 分钟收起（`gateway-config` 的 `IDLE_SECONDS`），数据都在 NAS，下次登录约 8 秒重建 |
| 改配置 | `kubectl patch configmap ...` 后，之后创建 / 重启的用户容器才生效；网关配置改完重启网关 |
| 轮换密钥 | 模型 Key、SM2 私钥：更新对应 Secret 后重启用户容器；信任凭据：与统一认证同时更换 `gateway-auth` 并重启网关 |
| 备份 | NAS 按贵方规范做定期快照：`users/`（会话与报告）、`kb/`（知识库，索引可由 `kb.py index` 重建） |
| 扩容 | 按需模式随集群扩节点；固定池化改 `--pool-size` 重新渲染、`kubectl apply -f pool.yaml` |
| 整体卸载 | `kubectl delete -f pool.yaml --ignore-not-found; kubectl delete namespace gaussdb-agent`（NAS 数据保留；PV 为 Retain，重新部署前解除旧绑定，见《完整手册》附录 B） |

## 17. 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 用户容器反复重启，日志 `mkdir: cannot create directory '/nas/me/...': Permission denied` | 个人目录被建成 root 属主 | `runtime-doctor.sh <工号> --fix` |
| 登录后等 2 分钟 504；用户容器 `ImagePullBackOff`，镜像名不带仓库前缀 | `USER_IMAGE_REGISTRY` 没填 | 填上（8.1），重启网关，删掉那个用户的 deploy 后重新登录 |
| 用户容器 `credproxy` 起不来，或连不上中间件 / 模型 | 网关与用户镜像版本不一致 | 两者用同一个 `TAG` |
| 网关 `CrashLoopBackOff`，日志「配置错误,网关拒绝启动」 | 缺配置或 Secret | 按日志补；8.4 之前出现属正常 |
| 网关日志「连不上 k8s API」 | `gateway-policy` 没放行 apiserver 的真实地址 | 8.6 第一条 |
| 登录数据库报「中间件接口路径前缀没有配置」 | `GRMP_PATH_PREFIX` 没填 | 8.5 填上，重启用户容器（固定池化重启池子的 Pod） |
| 登录数据库报「请求 …/common-operations 失败：HTTP 404」 | 路径前缀填错 | 向中间件团队核对 |
| 技能报「未注册脚本」或「脚本不存在」 | 白名单没导或不全 | 第 7 章导入并自检 |

**`agent-config`**（用户环境读，改了之后新建 / 重启的用户容器生效）：

| 键 | 说明 |
|---|---|
| `GRMP_API_HOST` / `GRMP_API_PORT` | 中间件地址 |
| `GRMP_PATH_PREFIX` | **必填**。中间件接口路径前缀，中间件团队提供 |
| `GRMP_APPKEY` | 中间件签名的 Appkey；空 = 不签名 |
| `GRMP_SIGN_MODE` | `full`（Appkey + Timestamp + Signature，私钥在 Secret `grmp-sm2`）/ `headers-only`（只发 Appkey + Timestamp，过渡期用） |
| `GRMP_SIGN_USER_ID` | SM2 签名的 userId，默认 `1234567812345678`（国标默认）；OpenSSL 默认是空串，用哪个问清中间件团队 |
| `GRMP_SIGN_TIMESTAMP` | `ms` / `s` |
| `GRMP_SIGN_FORMAT` / `GRMP_SIGN_ENCODING` | 签名格式 `raw` / `der`；编码 `hex` / `base64` |
| `GRMP_SIGN_PAYLOAD` | 被签名的串，默认 `{path}+{timestamp}` |
| `GRMP_USER_ID_HEADER` / `GRMP_USER_ID_PARAM` | 中间件要显式收调用人工号时，放在哪个请求头 / 报文顶层键；都空 = 不发 |
| `GRMP_INSTANCE_ALIASES` | 实例别名，`别名=实例IP/库名  # 说明`，换行或分号分隔 |
| `MODEL_BASE_URL` / `MODEL_ID` / `MODEL_PROVIDER_NAME` | 模型服务（OpenAI 兼容）地址、模型名、显示名 |
| `MODEL_INPUT_MODALITIES` | 模型能接收的输入，如 `text,image`；空 = 纯文本。只在模型确实支持图片时加 `image` |
| `GSDB_DASH_BASE_URL` | 回答里「打开报告」链接的站点前缀；空 = `/dash/...` |
| `KB_CLIP_ORIGINS` | 网页剪藏：允许剪藏的内网网站（`协议://主机[:端口]`，逗号分隔）；空 = 关闭。网关也读这一项，改完重启网关 |
| `KB_CLIP_MAX_MB` | 网页剪藏：单次剪藏（网页 + 页内图片）总大小上限，默认 30，最大 45 |

| 键 | 默认 | 说明 |
|---|---|---|
| `USER_IMAGE_REGISTRY` / `USER_IMAGE_TAG` | — | 用户容器镜像的仓库前缀与标签；`USER_IMAGE_TAG` 是升级开关 |
