# Top SQL（OpenGauss/GaussDB）

命中以下请求时，必须使用本 skill 并实际执行脚本，不要只做概念解释：

- 用户要求查看当前最耗时、最耗资源、最热点的 SQL
- 用户要求查看 Top SQL、SQL 排行榜、资源消耗榜
- 用户要求按总耗时、平均耗时、调用次数、逻辑读、返回行数对 SQL 排序
- 用户询问“哪些 SQL 最拖慢系统”“当前数据库最重的 SQL 是什么”这类需要真实排名结果的问题

典型触发语句：

- 给我最耗时的 SQL
- 查一下 top sql
- 看最耗资源的 SQL 排行榜
- 按平均耗时排一下前 10 条 SQL
- 按调用次数最多的 SQL 排行
- 哪些 SQL 最拖慢系统

执行规则：

0. **先判断用户问的是「累计」还是「最近一段时间」—— 这两个问题的答案常常完全不同。**

   `dbe_perf.statement` 是**自上次清零以来的累计值**。库跑了一个月、某条 SQL 最近十分钟
   突然冲高，那十分钟会被一个月的总量摊平，在累计榜上**根本看不见**。实测对比：累计榜
   第一名是一条累计 5963 秒的 UPDATE，而同一时刻最近 11 秒里真正在动的是另一条新语句
   （40 次、7.31 秒）——后者在累计榜上连前 50 都进不了。

   - 用户说「最近十分钟 / 刚才 / 这一会儿 / 突然变慢」这类**带时间的近况**：
     用 `--window 10m`（`2h`、`1d` 同理）。用户问**过去某个时间段**（「昨天下午三点那一阵」
     「10:46 到 11:07」）：用 `--from 'YYYY-MM-DD HH:MM' --to 'YYYY-MM-DD HH:MM'`
     （时间按**数据库所在时区**；不给 `--to` = 到此刻）。`--since-last` 仍是「距上次巡检」。

     **原则：不追求精确，只把用户说的时间段覆盖住，并告诉用户实际评估的是哪一段、为什么。**
     累计计数器只能在已有的时刻之间相减 —— WDR 快照、我们自己留的采样、此刻。脚本选
     「不晚于起点的最近一个时刻」到「不早于终点的最近一个时刻（或此刻）」，所以实际窗口
     通常**比用户要的宽**，宽出来的部分会把冲高摊薄。实例重启过时窗口不能跨过重启，
     只能覆盖重启之后那一段。脚本在表格后打一行「口径：你要看的是 … 实际评估的是 … 」，
     **这一行必须原样转达**（可以精简措辞，但「要的是哪段、评估的是哪段、为什么」三样不能少）。
     把「20:14 → 20:41 的增量」说成「最近 10 分钟」，用户会据此做判断，而那个判断没有依据。

     取不到快照也没有自留采样时：`--window` 退回「与已有基线相减 / 现场采一小段（最多 60 秒）」，
     口径行同样会写明实际覆盖了多久；`--from` 直接报错说明回看不了 —— 照实转达，不要改用累计榜冒充。

     **绝不为了凑满用户问的时长去阻塞等待。** `--live-sample` 才会阻塞，上限 300 秒，
     只在用户明确说「盯着看一会儿」时才用；日常提问一律用 `--window` / `--from` / `--since-last`。
     （第一版的 `--window 10m` 实现是 `sleep(600)`，实测把 opencode 整个挂住不出结果，
     而且测的是**未来**十分钟——用户问的是过去。）
   - 用户没提时间：照常给累计榜，**但必须把脚本输出里那句「累计了多久」一起转达**
     （例如「自 2026-10-17 10:41 起算，已累计 7.5 小时」），并提一句可以用
     `--window` / `--from` 看某段时间的变化。不说这句，用户会把几十天的总量当成现在的状况。

   增量模式下 `--by reads` 不可用（取数脚本里没有块数列，算不出增量），脚本会明确报错；
   可用 `time` / `avg` / `calls` / `rows` / `self` / `self_avg`。表格里带「窗口内新出现」标记的，是这段时间里
   才开始跑的语句——冲高往往就是它们。

   统计被清零（`reset_unique_sql`）或实例重启过时，增量算出来是负数，脚本会直接说
   「这个窗口算不出增量」。**照实转达，不要把它说成「最近没什么变化」。**

1. 如果用户只说“top sql / 最耗时 SQL / 最耗资源 SQL”，但没有指定排序维度：
   默认执行 `scripts/topsql.py -c <conn> --by time --limit 10`。
2. 如果用户明确指定排序维度：
   - 总耗时 / 最耗时 -> `--by time`
   - 平均耗时 -> `--by avg`
   - 调用次数 -> `--by calls`
   - 逻辑读 -> `--by reads`
   - 返回行数 -> `--by rows`
   - 不含等锁 / 自身耗时 / 实际消耗 CPU 最多 -> `--by self`；平均自身耗时 -> `--by self_avg`
     （自身耗时 = CPU + 数据 IO 时间，不含任何等待）
3. 如果用户明确指定要看前 N 条：
   把 N 映射到 `--limit N`；未指定时默认 `--limit 10`。
4. 如果用户没有提供连接名：
   **选择连接 —— 先登录，不要自己猜连接名。** 取数前确认已登录：
   `python3 {baseDir}/../gaussdb-login/scripts/login.py --status`。
   没有会话就先调 **gaussdb-login**：它读 `$GSDB_HOME/config.yaml`的首行 `connection_mode`，是 `gsql` 就把可选连接列成菜单让用户挑，是 `api` 就引导用户给出要访问的数据库。
   登录之后本 skill **不需要传 `-c`** —— 省略时自动用登录选定的那条连接；只有要临时换一个库时才显式传 `-c <连接名>`。
   **api 模式下每条命令都要带 `--session <句柄>`**：句柄是 gaussdb-login 在**本对话里**登录成功时输出的那一串（平台也可能按用户注入环境变量 `GSDB_SESSION`）。不带句柄的命令会被拒绝并提示「本对话未登录」——这时让用户先 gaussdb-login 登录，**不要自己挑一个**、不要猜、不要去看会话目录；别人的会话对本对话不可见，换一个对话要重新登录。
   **不要自己去读 config.yaml 挑名字**：不同应用下可能有同名连接，猜错会在另一个库上做诊断，而输出看起来完全正常。口令在 `{baseDir}/../common/credentials/*.enc`，由脚本解密，**你不要去读/解密它**。
5. 如果用户没有提供连接名，但当前只有一个连接：
   直接使用该连接。
6. 如果用户没有提供连接名，且存在多个连接：
   再询问要使用哪个连接。
7. 输出时优先返回真实 Top SQL 排名结果，并说明哪些 SQL 在主导整体负载、原因是什么；不要只解释“Top SQL 一般是干什么的”。
   **默认排除 GaussDB 自己的系统 SQL**（只访问系统表 / 系统视图 / 系统函数的语句：WDR 快照、监控采集、诊断工具——包括你自己——查系统视图的语句）。输出末尾的「已排除 N 条内核系统 SQL…」要转告用户，不要省略；用户明确要看系统 / 监控语句（如怀疑监控采集太重）时加 `--include-system`。
7b. **「等待占比」列——把被挡住的和自己慢的分开说。** 每张榜都带 `CPU+IO_S`（窗口模式为「窗口内CPU+IO(s)」）
   与「等待占比」= 1 −（CPU + 数据 IO）/ 总耗时。表下若有「#1、#2… 的耗时有 80% 以上不是 CPU / 数据 IO」那段，
   要告诉用户：这几条是**被挡住的**（等锁、等轻量锁、排队等 CPU、睡眠都可能），不是自己慢，排查走 `gaussdb-lockwait`；
   并给出（或建议跑）`--by self` / `--by self_avg` 的结果，回答「谁自己最慢 / 最耗资源」。
   **不要把「等待占比」说成「等锁占比」**：dbe_perf.statement 里没有单条语句的锁等待时间列，脚本分不出等的是哪一种。
   该列显示「—」并提示白名单待更新时，照实转达，不要自己估算。
8. 如果用户进一步要求查看某条 SQL 的完整文本：
   优先基于结果里的 `SQL_ID` 引导执行 `gaussdb-sqlfetch`；不要凭空编造完整 SQL 文本。
9. 如果用户进一步要求对某条 SQL 做执行计划或调优：
   引导进入 `gaussdb-explain` 或 `gaussdb-sqltune`，但前提是先把真实 Top SQL 结果查出来。
10. 脚本在标准错误里打出「已存入大盘:/dash/topsql?inst=…&by=…」时，在回答末尾附上这个链接。它是给用户看的页面地址（和对话页同一个网址），不是内部接口。**脚本给的是 Markdown 链接形态 `[打开报告](…)`，就按这个形态放进回答，不要把它改写成裸路径。** 裸的 `/dash/wdr?...` 用户点不开、复制到地址栏也打不开（实测过：用户要某个时间段的 WDR 报告，拿到裸路径之后跳不过去）。没有这一行（非容器环境，或存档失败）就不提大盘，**不要自己拼一个「大盘」地址出来**。

标准工作流：

1. 如果用户未指定排序维度，执行：

   ```bash
   python3 {baseDir}/scripts/topsql.py -c <conn> --by time --limit 10
   ```

2. 如果用户指定了排序维度和条数，按需执行，例如：

   ```bash
   python3 {baseDir}/scripts/topsql.py -c <conn> --by avg --limit 20
   ```

3. 如果用户问最近一段时间或某个时间段（规则 0），例如：

   ```bash
   python3 {baseDir}/scripts/topsql.py -c <conn> --window 10m
   python3 {baseDir}/scripts/topsql.py -c <conn> --from '2026-10-17 10:46' --to '2026-10-17 11:07'
   ```

   回答里先说「口径」那一行（要的是哪段、实际评估的是哪段、为什么），再给榜单。
