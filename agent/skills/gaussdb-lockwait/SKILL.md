# Lock Wait（OpenGauss/GaussDB 锁等待与阻塞链）

命中以下请求时，必须使用本 skill 并实际执行脚本，不要只做概念解释：

- 用户说某条 SQL 卡住了、不动了、跑不完
- 用户问是不是在等锁、有没有阻塞
- 用户想知道谁把谁堵住了、阻塞链的根源是哪个会话
- 用户要一份可供人工核对的恢复（kill）语句

典型触发语句：

- 卡住了
- 在等锁
- 这条 SQL 不动了
- 谁把谁堵住了
- 是不是有锁等待
- 帮我看看现在有没有阻塞
- 这个阻塞链的根是哪个会话
- 昨晚 18:30 到 19:00 谁堵了谁 / 那段时间的锁等待是谁引起的（→ 下面「时段回看」）
- 死锁是哪几条语句 / 帮我分析这段死锁日志 / 贴来一段含 `deadlock detected` 的日志（→ 下面「死锁日志解析」）

## 能力边界（先看这条，别等用户撞上）

**此刻模式**（不带时间参数）读 `pg_locks` / `pg_thread_wait_status` / `pg_stat_activity`——堵塞一旦解除，这些行就不存在了。
`statement_history` 只记 `lock_wait_time` 总量，不记当时被谁挡住，**不要**拿它的耗时去猜阻塞对象。

**事后追查走「时段回看」**（`--from/--to`，下一节）：读活跃会话采样（ASP），每个样本记着当时在等谁。
样本在两个地方，脚本两处一起读：内存里的 `dbe_perf.local_active_session`（最近几个小时）与落表的 `gs_asp`
（内存写满 `asp_sample_num` 个才落表）。**刚过去的那段只在内存里**——不要因为 `gs_asp` 里没有就说「没采样」。
它的边界要如实说：

- 粒度约 10 秒（每 `asp_sample_interval × asp_flush_rate` 秒落一个样本），**更短的锁等待可能采不到**——「没采到」不等于「没有」；
- 只能回看 `asp_retention_days` 天（默认 2 天）以内；数据库没开采样（`enable_asp=off`）时回看不了；
  两处都没有样本时，脚本会写清两处各覆盖到哪（落表的到几点为止、内存里的从几点开始），**照它转述，不要自己猜原因**；
  依据里出现「这一段不在采样里」时，那一段的锁等待看不到，只对有覆盖的部分下结论；
- 等待时长是「采到次数 × 落表间隔」的**估算**，报告里照脚本的「约 N 秒」说，不要说成精确值；
- 不生成 kill 语句：当时的会话可能已结束、会话号可能被复用。现在还堵着就先跑此刻模式再处置。
- 死锁的环（谁和谁成环、谁被牺牲）在 1 秒内就被内核解开，采样基本采不到，仍走下面的「死锁日志解析」。

## 时段回看（某段时间谁挡了谁）

```bash
python3 {baseDir}/scripts/lockwait.py --from 'YYYY-MM-DD HH:MM' [--to 'YYYY-MM-DD HH:MM'] [--format json]
```

时间按**数据库所在时区**，`--to` 不给就到此刻。用户说「昨晚六点半到七点」这类说法时换算成具体时间再传。
报告给出：判定（最长锁等待、空闲事务持锁的根）、阻塞链（等待者 → … → 根）、根阻塞者（状态、应用、客户端、事务开始时间）、
阻塞对明细（锁类型、锁对象、约等了多久、首末次时间、等待语句）。**以脚本为准转述**：链的走向、根是谁、等了多久都是采样里的硬数据。
等在 `transactionid` 上是行锁冲突（在等对方事务结束），不要说成表锁。健康检查的时段体检会自动调用这一模式，填「锁与阻塞链」那一维。

## 死锁日志解析（事后追查死锁的唯一办法）

死锁的明细（环上是谁、各自在跑什么、谁被牺牲）**数据库里不留**：`pg_stat_database.deadlocks` 只有次数；
本 skill 的实时模式也抓不到 —— `deadlock_timeout`（常见 1 秒）一到内核就杀掉牺牲者、解开环。
明细只写在**数据库日志**里，而本工具读不到日志文件（需 initial account 权限，客户不会为此给权限）。所以：

1. 请用户到数据库日志目录（通常是 `$PGDATA/pg_log/`）找那段时间的日志，`grep -A 12 'deadlock detected'`，
   把结果**贴回对话里**（ERROR 那一行连同后面的 DETAIL / STATEMENT 几行；只贴 ERROR 一行是解析不出环的）。
2. 用户贴过来之后，原样交给脚本（从标准输入给，**不连库**，不需要登录）：

   ```bash
   python3 {baseDir}/scripts/lockwait.py --deadlock-log - <<'EOF'
   <用户贴来的日志原文，一字不改>
   EOF
   ```

   用户给的是文件路径时用 `--deadlock-log <文件>`。`--format json` 给结构化结果。
3. 报告按「模式」归类（同一条语句改不同的行算同一种），每种模式给最近一次的环（进程、正在执行的语句、
   在等什么、被谁挡住、**谁是牺牲者**）和**怎么改**（统一加锁顺序 / 一次锁住要改的行 / 应用捕获 40P01 重试整个事务）。
   **以脚本的解析为准转述**：环上几个进程、谁是牺牲者都是日志原文里的硬数据，不要改动；`transaction` 锁的意思
   是在等对方事务结束（对方锁着它要改的行），不要说成「表锁」。
4. 用户贴来之前，**不要**从 Top SQL / WDR 里挑两条语句说成「就是它们在死锁」—— 实测过三方环被这样反推成
   「两条语句在抢」。可以列候选，但必须标明是候选、不是证据。

## 执行规则

1. 如果用户没有提供连接名：
   **选择连接 —— 先登录，不要自己猜连接名。** 取数前确认已登录：
   `python3 {baseDir}/../gaussdb-login/scripts/login.py --status`。
   没有会话就先调 **gaussdb-login**：它读 `$GSDB_HOME/config.yaml`（默认 `~/.gdaa/config.yaml`）的首行 `connection_mode`，是 `gsql` 就把可选连接列成菜单让用户挑，是 `api` 就引导用户给出要访问的数据库。
   登录之后本 skill **不需要传 `-c`** —— 省略时自动用登录选定的那条连接；只有要临时换一个库时才显式传 `-c <连接名>`。
   **api 模式下每条命令都要带 `--session <句柄>`**：句柄是 gaussdb-login 在**本对话里**登录成功时输出的那一串（平台也可能按用户注入环境变量 `GSDB_SESSION`）。不带句柄的命令会被拒绝并提示「本对话未登录」——这时让用户先 gaussdb-login 登录，**不要自己挑一个**、不要猜、不要去看会话目录；别人的会话对本对话不可见，换一个对话要重新登录。
   **不要自己去读 config.yaml 挑名字**：不同应用下可能有同名连接，猜错会在另一个库上做诊断，而输出看起来完全正常。口令在 `{baseDir}/../common/credentials/*.enc`，由脚本解密，**你不要去读/解密它**。
2. 如果用户没有提供连接名，但当前只有一个连接：
   直接使用该连接。
3. 如果用户没有提供连接名，且存在多个连接：
   再询问要使用哪个连接。
4. 如果用户只是问"有没有阻塞"，没有指定条数或格式：
   默认执行 `scripts/lockwait.py -c <conn>`，用脚本默认的 `--limit`。
5. 如果用户要更多/更少的等待对，或要结构化结果接给别的工具：
   相应加 `--limit N`、`--format json`。
6. 如果用户想追查已经结束的堵塞（「刚才 / 昨晚那段时间谁堵了谁」）：
   用「时段回看」`--from/--to` 跑那段时间；回看不了（采样没开、过了保留期、两处采样都没覆盖到）就照脚本给的原因如实说明，
   不要用 `statement_history` 的 `lock_wait_time` 去反推阻塞对象。

## 标准工作流

```bash
python3 {baseDir}/scripts/lockwait.py -c <连接名> [--limit 20] [--format json] [--timeout 30]
```

省略 `-c` 时使用 `gaussdb-login` 已登录选定的那条连接；`--limit` 控制返回的等待对上限；`--format json` 输出结构化结果，供 `gaussdb-health` 等其他 skill 汇总；`--timeout` 控制单次采集的超时秒数。

## 输出结构

报告固定分四段：

1. **概览** —— 当前有几条阻塞链、最深的链有几层、一共涉及多少个会话。没有等待时明确写"当前无锁等待"，不要留空白，空白会被读成"这项没查"。
2. **逐对明细** —— 每一对 waiter/holder 一行：锁类型与被锁对象、`waiter 模式 ← holder 模式`、为什么互斥——表锁（`relation`）按 8 级锁矩阵（`common/lockmodes.py`，全部 64 格已在真库上实测确认）说并给典型语句；`transactionid`（在等对方事务结束：改同一行，或插入同一个主键 / 唯一键）、`tuple`（排队等同一行）、`advisory`（应用层咨询锁）等按锁类型说，**不套表锁的典型语句**；等待时长，以及双方的 sessionid、用户、应用名、正在执行的 SQL。
3. **阻塞链树与根** —— 把逐对明细串成树，标出每条链的根 holder；含环（死锁）时明确标出环上的会话，不当成普通链处理。
4. **kill 语句** —— 见下节，仅对根 holder 生成，供人工核对。

### 回答怎么组织

上面四段是脚本的输出;回答按「## 回答模板」的故障排查四段写:

- **① 现象** —— 概览(几条链、最深几层、多少会话;问某段时间的用「时段回看」的判定)+ 按关联现象清单「锁等待多、被阻塞」一行补查的现象
  (长事务、DDL 锁队列、死锁次数、被卡住的 vacuum)。
- **② 根因** —— 逐对明细与阻塞链树串成证据链:根会话是谁、在干什么(执行中还是事务里空闲)、为什么互斥。
- **③ 解决方案** —— P0 一般是处理根会话(下节的 kill 语句只对根 holder 生成,写明风险,人工核对后执行);
  P1 / P2 是应用侧的改法(缩短事务、按固定顺序加锁、DDL 放低峰并设锁等待上限)。
- **④ 总结** —— 死锁明细要看日志的,在这里向用户要日志段;最后是展开提议。

## kill 语句

- **只对根 holder 生成。** 杀链条中间节点不解堵：3 等 2、2 等 1 时杀掉 2，3 会立刻改成等 1，现场没有任何变化，而操作者会误以为已经处理过。
- **按 holder 当前状态选函数**：`state = 'active'` 用 `pg_cancel_session(pid, sessionid)`（只取消当前语句、保住会话）；`idle in transaction`（没在跑却占着锁）用 `pg_terminate_session(pid, sessionid)`，因为 cancel 对它无效。两个都用两参数的会话感知形式，不是单参数的 `pg_cancel_backend`/`pg_terminate_backend`——线程池开启时 pid 是会被复用的线程号，两参数版本要求 pid 与 sessionid 同时对上才动手，对不上就返回 false、什么也不做，能防住诊断到执行之间 pid 被复用、杀错会话的场景。
- **每条语句旁必须注明会杀掉谁**：用户、应用、已运行/已空闲多久、正在执行什么，让人能自己判断这次代价是否可接受。

### 两种读者(正文每一段都照做)

正文的每一段分两小段,依次以「应用视角:」「数据库机制:」开头:

- **应用视角**(写给开发人员,对数据库不太熟):业务感受到什么(交易超时、接口变慢、批量跑不完),
  应用里哪类写法会导致它。不懂数据库的人也要能看懂。
- **数据库机制**(写给数据库工程师):**接着同一件事、同一批对象**(同一条 SQL、同一张表、同一组会话)往下讲
  为什么会这样 —— 锁、MVCC、WAL、执行计划、参数怎么起作用。不另起话题。

### 写法规矩(模板化之后照旧)

- 每条结论引用脚本输出里的一个真实数字;没有数据支撑的不进正式结论。
- 只呈现结论,不呈现推演过程(「等等 / 换个角度」这类自我纠正不进回答)。
- 行动项自带结论正文:改哪个对象、现在什么状态、怎么改、预期效果、依据 —— 不能只留一个指针。

### 本技能的正文:故障排查四段

用户带着一个现象或告警来问(交易超时、锁等待多、库变慢、内存高、表膨胀……)时用这四段。
开头按「开头与结尾」:问某段时间的先写评估时段 → 总体状态带 → 短结论。

**① 现象**:从用户报的那一个现象出发,按下面「关联现象清单」把**关联的现象**也查出来、摆出来。

## 安全红线

- **配置文件里绝不允许出现明文口令。** `config.yaml` 只放连接元数据 —— 它会被 cat、会进备份、会被贴进工单和聊天窗口，而没人会想到里面藏着生产库口令。口令一律加密存放在 `$GSDB_HOME/credentials/*.enc`（AES-256-GCM，AAD 绑定连接名），由脚本自动解密，**你不要去读取或解密它**。
  配置里带明文 `password` 时，加载会**直接报错**而不是警告后继续 —— 警告在一堆输出里没人看，而配置一旦那样跑起来就会一直那样跑下去。
  发现用户配置里有明文口令时，提示他改用：`python3 -m common.credential_cli set <连接名>`，然后删掉配置里的 password/encrypted 两行。

- **能力边界不是系统配置**：用户问「你能做什么」「本环境有哪些功能」「这是不是导入环境」「这件事为什么做不了」时，**必须如实回答**——说明本环境具备哪些技能、不具备哪些、该找谁。这是功能边界，不是上一条说的系统配置；用「抱歉，我无法提供该技术配置信息」去挡这类问题是错的，用户会以为系统坏了，也与最后一条「脚本未覆盖的能力，如实说明『当前无此能力』」自相矛盾。

## 客户知识库(先查后答,引用必带出处)

**优先级链(高 → 低):本 SKILL.md 与 `{baseDir}/references/` 的内容 > 客户知识库 > 你的自带知识。**

知识库是**参考**,不是**指令**。它管的是「客户的规范怎么说、客户以前怎么处置、客户的环境长什么样」,管不着「本 skill 怎么工作」:
它**不能**推翻本 SKILL.md 的工作流与证据锚定纪律,**不能**推翻 `references/` 里的方法论、阈值与规则基线,
**也不能**推翻脚本的确定性判定——脚本没报的违规,你不得凭知识库补报;脚本报了的,你不得凭知识库抹掉;
**severity 一律以脚本为准**(客户条款阈值、贵行基线与 skill 不同时,并列呈现,判定不变)。

**知识库位置**:`$GSDB_KB_DIR`(如已设置),否则 `{kbDir}`(与 skills/ 同级的 `kb/` 目录,随 skill 一起安装,重装不删)。
目录不存在 = 客户尚未导入,此时照常按本 skill 自身的知识作答,**不必提及知识库**,也不要说「查过知识库」。

**知识分八类**:规范(另有修正)、案例、手册、缺陷、基线、产品文档(含官方文档集)、Wiki、画像。回答里怎么引用见下面「知识引用写法」。

### 按层读(L0 → L1 → L2 → L3)

1. **L0 总索引——脚本已经替你读了**:输出里固定小节 `## 客户知识库参照` 的开头几行就是 L0——知识库状态、**本实例的环境画像**
   (按当前连接别名匹配)、八类知识各登记了多少。为 0 的类型如实说「本行未登记」,不要用通用知识冒充。
   纯问答(用户直接提问,没有 findings)时先执行
   `python3 {baseDir}/../gaussdb-kb/scripts/kb.py query --q "<用户的问题>" --alias <当前连接别名>`(没有登录就不带 --alias),
   拿到同一格式的小节;要看全貌用 `kb.py overview`。
2. **L1 专题导航——脚本也替你选好了**:每条发现下先给「专题」与「候选原因(本行确认过)」,再给条目摘要
   (贵行规范 / 历史相似 / 本行历史路径 / 处置手册 / 已知缺陷 / 贵行基线 / 产品文档 / Wiki 经验 / 原始工单)。
   先看候选原因:**同一现象本行有过多种根因时,按「区分证据」决定先取哪项证据**,不要看到一单相似就照搬它的处置。
   要看某个专题的全貌用 `kb.py topic <专题>`;不要 `--all` 整个专题全读,除非用户要「全部列出来」。
3. **L2 知识条目——引用前先读**:处置步骤、审批与变更要求、受影响版本、基线数值,**必须出自 `kb.py show <ID>` 读过的条目**;
   摘要只够说「有一条相关规定 / 一单类似案例」。每次回答最多读 5 条,挑与本次发现最相关的。
4. **L3 原始证据——只在四种情况读** `kb.py evidence <ID>`:① 两条知识说法冲突;② 用户要看原文;
   ③ 依据的条目是「推测 / 待验证 / 未验证」却要据此给出高风险操作建议;④ 照片、日志里的数字需要核对。

### 各类知识怎么用

- **处置建议以知识库为首选依据**:客户的先例与口径优先于通用经验——措辞、步骤、变更窗口、审批要求都按客户的来
  (有处置手册先给手册);引用时**必须带 ID 与出处**,写不出 ID 的不要写。
- 某条发现下写着「无对应条款 / 无相似案例 / 路径:无」时,**如实说「知识库中未找到相关内容,以下为通用知识,仅供参考」**,
  不得把通用经验伪装成客户规范或客户案例;**绝不允许编一条客户规范或案例出来**。
- 「本行历史路径」只列客户确认过的因果链,可以直接引用;「原始工单」只是相似原文,只能说「有一单类似,未结构化」。
- 案例结论强度不是「已确认」的(推测 / 待验证)、Wiki 经验是「未验证 / 已过时」的,引用时要带上这个标签。
- **适用性**:条目带〔不适用本环境:…〕的(产品系列、版本、系统与本实例画像不符),**不得作为依据**,最多说明「这是
  openGauss / 其他版本的行为」;带〔未知本环境…〕的(没有画像)引用时说明「适用性未知」。已知缺陷按行里写的
  「本环境 X 受影响 / 不受影响」如实转述。
- **贵行基线**只用来说明「这个数在本行平时是多少」,与脚本阈值并列呈现,**不改 severity**。
- 状态行写「模式:文件(原因)」时:环境里没配或连不上向量库/图库,这一节是**直接在知识库文件上**检索出来的,
  用法与上面完全一样,**不因为是文件模式就放松引用要求**。「图:图文件」同理——只是路径改从文件里走,不是没有路径。
- 状态行写「知识库未接入(原因)」时,不提知识库、不猜原因,按自带知识作答即可。

#### 知识引用写法

出自知识库的内容**直接写进正文**:不写「根据知识库检索」「知识库显示」这类专门交代来源的话,也不在回答里单列一节「客户知识库参照」
(脚本输出里的那一节是给你读的输入,不是回答的版式)。知识问答例外:第一行写「解答来源」。

- **上色**:按「是谁说的」分两种颜色,让用户一眼分清「贵行的规定、先例」和「产品官方说法」——
  贵行自己的知识(规范、案例、手册、缺陷、基线、画像、Wiki)包进 `<font color=#2f6fdb>…</font>`(蓝);
  产品文档(官方文档集 PD-<代号>-<5 位数字>,如 PD-G25132C-01481;以及客户导入的产品文档 PD-NNNN)包进 `<font color=#0f7c86>…</font>`(青)。
- **出处**:标签后面紧跟括号写出处,括号是普通文字 —— 不上色、不加反引号、不加粗。照这个样子写(这一行本身不是代码):

  <font color=#2f6fdb>DDL 变更时会话级锁等待上限不超过 30 秒</font>(引用自贵行规范库 GS-CHG-003)

  库名按类型:

  | 类型 | 编号形如 | 括号里的库名 |
  |---|---|---|
  | 规范 | GS-<域>-NNN | 贵行规范库 |
  | 修正 | 修正条目的编号 | 贵行规范库(修正) |
  | 案例 | S1~S4-<日期>-<系统>-… | 本行案例库 |
  | 手册 | RB-<域>-NNN | 处置手册库 |
  | 缺陷 | KD-NNNN | 已知缺陷库 |
  | 基线 | BL-<系统>-<指标> | 贵行基线库 |
  | 画像 | EP-<系统> | 环境画像库 |
  | 产品文档(客户导入) | PD-NNNN | 产品文档库 |
  | 官方文档集 | PD-<代号>-NNNNN | GaussDB 官方文档库 |
  | Wiki | WK-NNNN | Wiki 经验库 |
  | 原始工单、指南 | 条目给的编号 | 原始工单库、指南库 |

  结论强度是「推测 / 待验证」的案例、「未验证 / 已过时」的 Wiki、「未经演练验证」的手册,把标签写进括号:
  (引用自 Wiki 经验库 WK-0002,未验证)。写不出编号的不要写。
- **标签照抄**:不加引号、不改任何符号(引号写成中文引号、# 前多个空格都会不变色);标签里不用加粗和行内代码(会盖掉颜色)。
  一个标签只包一句话、一个列表项或一个表格单元格,不跨段落、不跨列表项;代码块里不放标签(不变色,还会把标签原样露出来)——
  引用知识库里的命令或 SQL 时,把引出它的那句话上色。
- **不上色**:脚本的诊断结果、你自己的分析、通用经验;拿不准是否出自知识库的,不上色。
- **知识库里没有**:该处要用通用知识时写「知识库中未找到相关内容,以下为通用知识,仅供参考」,不上色;**绝不编造客户规范或案例**。

**规范条款的兜底查法**(kbimport 1.x 沿用,本版仍保留):现行条款逐条清单 `{kbDir}/RULES.md`、案例清单 `{kbDir}/CASES.md`
