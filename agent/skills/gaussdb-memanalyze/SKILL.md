# Mem Analyze（OpenGauss/GaussDB 动态内存分析）

脚本只读采集六层证据并按阈值产**确定性发现**；你负责解读、归因、排优先级、给整改方案。
**判定归脚本，判断归你**——不要自己重新算数字，也不要隐瞒脚本报出的发现。

命中以下请求时，必须使用本 skill 并实际执行脚本，不要只做概念解释：

- 用户要排查内存为什么满了或突然冲高
- 用户要定位是谁、哪条 SQL、哪个算子在吃内存
- 用户要判断是不是内存泄漏或 work_mem/并发设置过高

典型触发语句：

- 内存怎么满了
- 内存被谁吃了
- 哪条 SQL 吃内存
- 哪个算子吃内存
- 是不是内存泄漏

## 工作流

1. **选择连接 —— 先登录，不要自己猜连接名。** 取数前确认已登录：
   `python3 {baseDir}/../gaussdb-login/scripts/login.py --status`。
   没有会话就先调 **gaussdb-login**：它读 `$GSDB_HOME/config.yaml`的首行 `connection_mode`，是 `gsql` 就把可选连接列成菜单让用户挑，是 `api` 就引导用户给出要访问的数据库。
   登录之后本 skill **不需要传 `-c`** —— 省略时自动用登录选定的那条连接；只有要临时换一个库时才显式传 `-c <连接名>`。
   **api 模式下每条命令都要带 `--session <句柄>`**：句柄是 gaussdb-login 在**本对话里**登录成功时输出的那一串（平台也可能按用户注入环境变量 `GSDB_SESSION`）。不带句柄的命令会被拒绝并提示「本对话未登录」——这时让用户先 gaussdb-login 登录，**不要自己挑一个**、不要猜、不要去看会话目录；别人的会话对本对话不可见，换一个对话要重新登录。
   **不要自己去读 config.yaml 挑名字**：不同应用下可能有同名连接，猜错会在另一个库上做诊断，而输出看起来完全正常。口令在 `{baseDir}/../common/credentials/*.enc`，由脚本解密，**你不要去读/解密它**。

2. **选模式。** 按用户描述的时点选，三选一：

   ```bash
   # a) 现场：内存此刻正高（最常用）
   python3 {baseDir}/scripts/memanalyze.py snapshot -c <conn> --top 20

   # b) 事后：冲高已经过去（只能读 WLM 历史表）
   python3 {baseDir}/scripts/memanalyze.py history -c <conn> --top 20

   # c) 判泄漏还是尖峰：持续采样看趋势
   python3 {baseDir}/scripts/memanalyze.py watch -c <conn> --interval 5 --count 12
   ```

   需要机器可读结果时加 `--format json`。

4. **先读「能力与视图探测」节，再读数字。** 这一节说明每层用的是哪个视图、哪些层**没有数据**。
   标 ✗ 的层是**盲区**，不是「没问题」。你必须在结论里明确说明哪些层是盲的、为什么盲——
   典型是 `resource_track_level = query` 导致算子级不可用。**绝不能**因为算子表是空的就说
   「算子层无异常」。

5. **按下钻链条归因，不要平铺。** 六层是有因果顺序的，照这个顺序读：

   - **L1** 先定性：冲的是 `dynamic_used_memory` 还是 `shared_used_memory`？
     `dynamic_peak_memory` 远高于当前值 → 冲高已发生但已结束（`MEM_PEAK_FALLBACK`）。
   - **L2** 定根因类型：某个 context（尤其 `CacheMemoryContext`）长期占大头 → 指向
     **泄漏 / 元数据缓存膨胀 / 会话不释放**；执行器类 context 占大头 → 指向**真在干活**。
     这两类根因的整改方向完全相反，先分清再往下走。
   - **L3 → L4 → L5** 是同一条线索的收敛：哪个会话 → 它在跑哪条 SQL → 那条 SQL 的哪个算子。
     报告里 L4 和 L5 用 `query_id` 关联，**你要显式把这条链讲出来**，例如：
     「动态内存 95% → etl 会话峰值 4.1 GB → query_id 90210 → 算子 #3 Vector Sort 峰值 3.8 GB、
     下盘 2.5 GB」。
   - **L6** 最后回头看：`MEM_CONFIG_OVERCOMMIT` 说明 `work_mem × max_connections` 理论上限
     本就超过动态内存上限——这是**配置性风险**，不是必然发生，别把它说成当前故障的直接原因。

6. **抓典型根因信号。**
   - `MEM_SQL_ESTIMATE_OFF` / `MEM_OP_ROWS_OFF`（估算与实际差 10× 以上）→ 统计信息过期，
     建议 `ANALYZE` 相关表 [需人工执行]。
   - `MEM_OP_SPILL` / `MEM_SQL_SPILL`（下盘）→ work_mem 不足以容纳该算子。**先定位到具体算子
     再谈调 work_mem**，不要一上来就建议全局调大——全局调大会放大 `MEM_CONFIG_OVERCOMMIT` 风险。
   - `MEM_SESSION_IDLE_XACT` → 空闲事务占着内存不放，查应用连接池是否未提交事务。
   - `MEM_CONTEXT_DOMINANT` + `watch` 判出 `MEM_TREND_LEAK` → 才可以说「疑似泄漏」；
     单次快照**不足以**下泄漏结论，要建议跑 `watch` 确认。
   - `MEM_TREND_SPIKE`（尖峰后回落）→ 指向单次大查询，不是泄漏。

7. **证据锚定校验。** 你写进报告的每个数字（百分比、内存值、`query_id`、`plan_node_id`、
   算子名）必须能在脚本输出里**逐字**找到。找不到就不要写。禁止凭印象补充脚本没报的发现，
   禁止改动脚本给出的 severity。

8. **加载方法论。** 需要深入归因时，阅读 `{baseDir}/references/memory-methodology.md`
   （根因判定树）与 `{baseDir}/references/gaussdb-memory-internals.md`（内存架构背景）。

9. **交棒。** 定位到具体 SQL 后，可转 `sqltune` skill 做 hypopg 实证优化；
   涉及整体健康度转 `health`；要看一段时间的库级表现转 `wdr`。

10. **退出码语义。** `0` = 脚本跑成功（**不代表内存没问题**，结论在 stdout）；
   `1` = 运行错误；`2` = 连接/配置错误。不要把退出码 0 解释为「内存正常」。

### 回答怎么组织

按「## 回答模板」的故障排查四段写:

- **① 现象** —— L1 定性(动态还是共享内存、峰值是否已过去)+ 按关联现象清单「内存高」一行补查的现象(会话数、大排序 / 哈希、存储过程)。
- **② 根因** —— 按第 5 步的 L2 → L5 下钻写成一条证据链(哪个 context → 哪个会话 → 哪条 SQL → 哪个算子);
  L6 的配置性风险单独一句,不说成这次冲高的直接原因。
- **③ 解决方案** —— P0 / P1 / P2,按第 6 步的典型根因信号给改法(先定位到算子再谈 work_mem;疑似泄漏先建议 watch 确认)。
- **④ 总结** —— 第 9 步的交棒建议放在这里;最后是展开提议。

## 能力边界（如实说明，不要假装）

- **算子级（L5）需要 `resource_track_level = operator`**（默认是 `query`），
  **历史回溯需要 `enable_resource_record = on`**（默认 `off`）。没开就是没数据，
  脚本会明确报出 GUC 名与目标值。**这是环境限制，不是脚本缺陷**，如实转达并标注 `[需人工执行]`，
  不要绕过、不要猜数据。
- **L4 / L5 视图在却没数据时**，脚本把这一层的前置参数连同本实例的当前值逐个列出来
  （`enable_resource_track`、`use_workload_manager`、`resource_track_level`、`resource_track_cost`，history 再加
  `enable_resource_record`、`resource_track_duration`）：有没满足的就照它报 `[需人工执行]`；**都满足仍为空**
  的（当时没有够格的作业，或内核不填 —— openGauss-lite 单机实测不填 WLM 作业视图），如实说「这一层看不到」，落盘去看 `gaussdb-wdr`
  的 `WDR_TEMP_SPILL` 与 Top SQL 溢出列，**不要说成「没有大内存 SQL」**。值显示「?（没读到）」是没取到，不是 off。
- **L3「已用」为负的行标了「不可信」**：线程池下按行的内存计数会被减成负数。这几行的已用不能当用量，
  峰值只当下限参考，不要拿它们排序或下结论。
- **视图是运行时探测的**：openGauss 与 GaussDB、集中式与分布式的内存视图名与列集都不同。
  脚本会选它能找到的最优视图并在报告里印出来。某层所有候选视图都不存在时，
  说明该环境不提供这类数据，如实说明。
- **`history` 模式下 L1/L2/L3 必然不可用**：它们是实时视图，冲高过去就查不到了。
  只有 WLM 历史表留下了当时的 SQL 与算子内存。这是事实，不是失败。
- **单次 `snapshot` 无法区分泄漏与尖峰**。要下「泄漏」结论必须跑 `watch`。

### 开头与结尾(所有回答)

1. **评估时段**(只在问某段时间时):第一行先说清要的是哪段、实际评估的是哪段、为什么不同(快照边界、保留期)。
2. **总体状态带**(有总体级别的回答):脚本给的总体级别 + 「驱动:」一句;脚本给了判断校验徽章的,下一行照抄。
   **级别一律以脚本判定为准**:不下调、不补报脚本没报的问题。
3. **短结论**:2–4 句,先说结论再说原因,开发人员也看得懂;不能出现比总体状态更轻的定性。
4. **正文**:按下面「本技能的正文」分段,段标题照写(① ② ③ ④)。
5. **展开提议**:最后用 1–3 个**问句**收尾,每句一个深入方向,句式固定:「需要就 xxx 展开说明吗?」
   (或「需要我 xxx 吗?」)。不要写成「需要的话可以继续:① … ② …」这种陈述句 —— 用户要的是一眼能回答「要 / 不要」的问题。
   需要用户配合的事(提供日志、确认业务情况、到测试环境实测)单独写在总结里,不和展开提议混在一起。
   **提议不能替代正文**:正文该写的结论、证据、方案不能省掉、留到「需要再展开」。

### 两种读者(正文每一段都照做)

正文的每一段分两小段,依次以「应用视角:」「数据库机制:」开头:

- **应用视角**(写给开发人员,对数据库不太熟):业务感受到什么(交易超时、接口变慢、批量跑不完),
  应用里哪类写法会导致它。不懂数据库的人也要能看懂。
- **数据库机制**(写给数据库工程师):**接着同一件事、同一批对象**(同一条 SQL、同一张表、同一组会话)往下讲
  为什么会这样 —— 锁、MVCC、WAL、执行计划、参数怎么起作用。不另起话题。

讲机制也要落到这次采到的数字上;没有证据,不提内核参数调整。

### 写法规矩(模板化之后照旧)

- 每条结论引用脚本输出里的一个真实数字;没有数据支撑的不进正式结论。
- 只呈现结论,不呈现推演过程(「等等 / 换个角度」这类自我纠正不进回答)。
- 行动项自带结论正文:改哪个对象、现在什么状态、怎么改、预期效果、依据 —— 不能只留一个指针。
- 问的是过去的时间段时,事后看不到的现象(例如当时的内存上下文分布)写「这一项回看不了」,不拿现在的状态冒充当时;
  能回看的(锁与阻塞链有活动会话采样,见 gaussdb-lockwait 的时段回看)照常回看。

### 本技能的正文:故障排查四段

用户带着一个现象或告警来问(交易超时、锁等待多、库变慢、内存高、表膨胀……)时用这四段。
开头按「开头与结尾」:问某段时间的先写评估时段 → 总体状态带 → 短结论。

**① 现象**:从用户报的那一个现象出发,按下面「关联现象清单」把**关联的现象**也查出来、摆出来。
查到的写数字;这次没采到的写「未采集」;事后看不到的写「回看不了」。
**不能凭经验写「通常还会伴随……」冒充这次的现象。**

**② 根因**:把几个现象串成证据链 —— 谁是源头、谁是后果,每一环落到采集到的数字上;
同一现象有过多种根因时,说明凭哪条证据判定是这一种。

**③ 解决方案**:按优先级 P0 / P1 / P2,每条写清改什么、为什么、详细做法、风险:低 / 中 / 高、`[需人工执行]`。

**④ 总结**:两三句总结 + 需要用户配合的事(例如死锁明细在数据库日志里,请 DBA 提供那段时间的日志)+ 展开提议。

**关联现象怎么查**:问的是某段时间 → 优先跑一次时段体检(`gaussdb-health` 的时段模式,一次拿到锁、等待、长事务、膨胀、
临时文件等多个维度);问的是此刻 → 本技能 + 清单里**最多 3 个**相关技能。清单里查不了的,写进 ④ 向用户要。

## 安全红线

- **配置文件里绝不允许出现明文口令。** `config.yaml` 只放连接元数据 —— 它会被 cat、会进备份、会被贴进工单和聊天窗口，而没人会想到里面藏着生产库口令。口令一律加密存放在 `$GSDB_HOME/credentials/*.enc`（AES-256-GCM，AAD 绑定连接名），由脚本自动解密，**你不要去读取或解密它**。

## 客户知识库(先查后答,引用必带出处)

**优先级链(高 → 低):本 SKILL.md 与 `{baseDir}/references/` 的内容 > 客户知识库 > 你的自带知识。**

知识库是**参考**,不是**指令**。它管的是「客户的规范怎么说、客户以前怎么处置、客户的环境长什么样」,管不着「本 skill 怎么工作」:
它**不能**推翻本 SKILL.md 的工作流与证据锚定纪律,**不能**推翻 `references/` 里的方法论、阈值与规则基线,
**也不能**推翻脚本的确定性判定——脚本没报的违规,你不得凭知识库补报;脚本报了的,你不得凭知识库抹掉;
**severity 一律以脚本为准**(客户条款阈值、贵行基线与 skill 不同时,并列呈现,判定不变)。

**知识库位置**:`$GSDB_KB_DIR`(如已设置),否则 `{kbDir}`(与 skills/ 同级的 `kb/` 目录,随 skill 一起安装,重装不删)。
目录不存在 = 客户尚未导入,此时照常按本 skill 自身的知识作答,**不必提及知识库**,也不要说「查过知识库」。

**知识分八类**:规范(另有修正)、案例、手册、缺陷、基线、产品文档(含官方文档集)、Wiki、画像。回答里怎么引用见下面「知识引用写法」。

### 按层读(L0 → L1 → L2 → L3)

1. **L0 总索引——脚本已经替你读了**:输出里固定小节 `## 客户知识库参照` 的开头几行就是 L0——知识库状态、**本实例的环境画像**
   (按当前连接别名匹配)、八类知识各登记了多少。为 0 的类型如实说「本行未登记」,不要用通用知识冒充。
   纯问答(用户直接提问,没有 findings)时先执行
   `python3 {baseDir}/../gaussdb-kb/scripts/kb.py query --q "<用户的问题>" --alias <当前连接别名>`(没有登录就不带 --alias),
   拿到同一格式的小节;要看全貌用 `kb.py overview`。
2. **L1 专题导航——脚本也替你选好了**:每条发现下先给「专题」与「候选原因(本行确认过)」,再给条目摘要
   (贵行规范 / 历史相似 / 本行历史路径 / 处置手册 / 已知缺陷 / 贵行基线 / 产品文档 / Wiki 经验 / 原始工单)。
   先看候选原因:**同一现象本行有过多种根因时,按「区分证据」决定先取哪项证据**,不要看到一单相似就照搬它的处置。
   要看某个专题的全貌用 `kb.py topic <专题>`;不要 `--all` 整个专题全读,除非用户要「全部列出来」。
3. **L2 知识条目——引用前先读**:处置步骤、审批与变更要求、受影响版本、基线数值,**必须出自 `kb.py show <ID>` 读过的条目**;
   摘要只够说「有一条相关规定 / 一单类似案例」。每次回答最多读 5 条,挑与本次发现最相关的。
4. **L3 原始证据——只在四种情况读** `kb.py evidence <ID>`:① 两条知识说法冲突;② 用户要看原文;
   ③ 依据的条目是「推测 / 待验证 / 未验证」却要据此给出高风险操作建议;④ 照片、日志里的数字需要核对。

### 各类知识怎么用

- **处置建议以知识库为首选依据**:客户的先例与口径优先于通用经验——措辞、步骤、变更窗口、审批要求都按客户的来
  (有处置手册先给手册);引用时**必须带 ID 与出处**,写不出 ID 的不要写。
- 某条发现下写着「无对应条款 / 无相似案例 / 路径:无」时,**如实说「知识库中未找到相关内容,以下为通用知识,仅供参考」**,
  不得把通用经验伪装成客户规范或客户案例;**绝不允许编一条客户规范或案例出来**。
- 「本行历史路径」只列客户确认过的因果链,可以直接引用;「原始工单」只是相似原文,只能说「有一单类似,未结构化」。
- 案例结论强度不是「已确认」的(推测 / 待验证)、Wiki 经验是「未验证 / 已过时」的,引用时要带上这个标签。
- **适用性**:条目带〔不适用本环境:…〕的(产品系列、版本、系统与本实例画像不符),**不得作为依据**,最多说明「这是
  openGauss / 其他版本的行为」;带〔未知本环境…〕的(没有画像)引用时说明「适用性未知」。已知缺陷按行里写的
  「本环境 X 受影响 / 不受影响」如实转述。
- **贵行基线**只用来说明「这个数在本行平时是多少」,与脚本阈值并列呈现,**不改 severity**。
- 状态行写「模式:文件(原因)」时:环境里没配或连不上向量库/图库,这一节是**直接在知识库文件上**检索出来的,
  用法与上面完全一样,**不因为是文件模式就放松引用要求**。「图:图文件」同理——只是路径改从文件里走,不是没有路径。
- 状态行写「知识库未接入(原因)」时,不提知识库、不猜原因,按自带知识作答即可。

#### 知识引用写法

出自知识库的内容**直接写进正文**:不写「根据知识库检索」「知识库显示」这类专门交代来源的话,也不在回答里单列一节「客户知识库参照」
(脚本输出里的那一节是给你读的输入,不是回答的版式)。知识问答例外:第一行写「解答来源」。

- **上色**:按「是谁说的」分两种颜色,让用户一眼分清「贵行的规定、先例」和「产品官方说法」——
  贵行自己的知识(规范、案例、手册、缺陷、基线、画像、Wiki)包进 `<font color=#2f6fdb>…</font>`(蓝);
  产品文档(官方文档集 PD-<代号>-<5 位数字>,如 PD-G25132C-01481;以及客户导入的产品文档 PD-NNNN)包进 `<font color=#0f7c86>…</font>`(青)。
- **出处**:标签后面紧跟括号写出处,括号是普通文字 —— 不上色、不加反引号、不加粗。照这个样子写(这一行本身不是代码):

  <font color=#2f6fdb>DDL 变更时会话级锁等待上限不超过 30 秒</font>(引用自贵行规范库 GS-CHG-003)

  库名按类型:

  | 类型 | 编号形如 | 括号里的库名 |
  |---|---|---|
  | 规范 | GS-<域>-NNN | 贵行规范库 |
  | 修正 | 修正条目的编号 | 贵行规范库(修正) |
  | 案例 | S1~S4-<日期>-<系统>-… | 本行案例库 |
  | 手册 | RB-<域>-NNN | 处置手册库 |
  | 缺陷 | KD-NNNN | 已知缺陷库 |
  | 基线 | BL-<系统>-<指标> | 贵行基线库 |
  | 画像 | EP-<系统> | 环境画像库 |
  | 产品文档(客户导入) | PD-NNNN | 产品文档库 |
  | 官方文档集 | PD-<代号>-NNNNN | GaussDB 官方文档库 |
  | Wiki | WK-NNNN | Wiki 经验库 |
  | 原始工单、指南 | 条目给的编号 | 原始工单库、指南库 |

  结论强度是「推测 / 待验证」的案例、「未验证 / 已过时」的 Wiki、「未经演练验证」的手册,把标签写进括号:
  (引用自 Wiki 经验库 WK-0002,未验证)。写不出编号的不要写。
- **标签照抄**:不加引号、不改任何符号(引号写成中文引号、# 前多个空格都会不变色);标签里不用加粗和行内代码(会盖掉颜色)。
  一个标签只包一句话、一个列表项或一个表格单元格,不跨段落、不跨列表项;代码块里不放标签(不变色,还会把标签原样露出来)——
  引用知识库里的命令或 SQL 时,把引出它的那句话上色。
- **不上色**:脚本的诊断结果、你自己的分析、通用经验;拿不准是否出自知识库的,不上色。
- **知识库里没有**:该处要用通用知识时写「知识库中未找到相关内容,以下为通用知识,仅供参考」,不上色;**绝不编造客户规范或案例**。

**规范条款的兜底查法**(kbimport 1.x 沿用,本版仍保留):现行条款逐条清单 `{kbDir}/RULES.md`、案例清单 `{kbDir}/CASES.md`
