# Health Check（OpenGauss/GaussDB 数据库健康检查）

一次性、只读、可信的数据库健康检查。**确定性归脚本（采集 + 阈值发现），判断归你（LLM），但你的判断必须对脚本的 `## Deterministic Findings` 做证据锚定校验。** 报告抬头用确定性状态带，不编造单一分数。

**本技能是汇总层，不是唯一的证据来源。** `{baseDir}/scripts/health.py` 自己只读采集 9 个本地维度（Overview / Slow SQL / 长事务 / 连接 / Checkpoint·WAL·归档 / 复制 / Schema / 占用量 / 并发），另外以子进程方式各跑一次 `gaussdb-lockwait`、`gaussdb-waitevent`、`gaussdb-vacuum` 三个 skill 的 `--format json` 输出，把它们的 `Deterministic Findings` 并入本报告——锁堵塞、等待事件/DB time、死元组/膨胀这三块的**完整证据、原始表、阻塞链/下钻分析都在对应子 skill 里**，本技能只搬运它们已经算出来的风险结论，并在每条这样的 finding 后面标注来源（`（详见 gaussdb-xxx）`）。**要看某一块的全部细节，直接单独跑那个子 skill，不要指望 health 的报告重现它。** 连接元数据读取 `$GSDB_HOME/config.yaml`，凭据由脚本从 `{baseDir}/../common/credentials/` 自动解密。

命中以下请求时，必须使用本 skill 并实际执行脚本，不要只做概念解释：

- 用户要判断数据库是否健康
- 用户要排查卡顿、阻塞、长事务、膨胀、复制延迟、checkpoint 压力
- 用户要一次性看整体健康检查结果，而不是只看单一指标

典型触发语句：

- 库健康吗
- 为什么卡
- 有没有阻塞
- 有没有长事务
- 有没有膨胀
- 复制有没有延迟
- 最近半小时库怎么样 / 帮我看下 10:46 到 11:07 这段时间（→ 时段体检，见工作流第 2 步末尾）

## 工作流

1. **选择连接 —— 先登录，不要自己猜连接名。** 取数前确认已登录：
   `python3 {baseDir}/../gaussdb-login/scripts/login.py --status`。
   没有会话就先调 **gaussdb-login**：它读 `$GSDB_HOME/config.yaml`的首行 `connection_mode`，是 `gsql` 就把可选连接列成菜单让用户挑，是 `api` 就引导用户给出要访问的数据库。
   登录之后本 skill **不需要传 `-c`** —— 省略时自动用登录选定的那条连接；只有要临时换一个库时才显式传 `-c <连接名>`。
   **api 模式下每条命令都要带 `--session <句柄>`**：句柄是 gaussdb-login 在**本对话里**登录成功时输出的那一串（平台也可能按用户注入环境变量 `GSDB_SESSION`）。不带句柄的命令会被拒绝并提示「本对话未登录」——这时让用户先 gaussdb-login 登录，**不要自己挑一个**、不要猜、不要去看会话目录；别人的会话对本对话不可见，换一个对话要重新登录。
   **不要自己去读 config.yaml 挑名字**：不同应用下可能有同名连接，猜错会在另一个库上做诊断，而输出看起来完全正常。口令在 `{baseDir}/../common/credentials/*.enc`，由脚本解密，**你不要去读/解密它**。
2. **采集证据——一条命令，中途不停。**

   ```bash
   python3 {baseDir}/scripts/health.py -c <conn>
   ```

   只读。本地 8 个采集器产固定小节：`## Overview`、`## Slow SQL`、`## Long & Idle Transactions`、`## Connections`、`## Checkpoint / WAL / Archiving`、`## Replication / Standby`、`## Schema / Objects`、`## Transactions / Concurrency`；另外后台跑三个子 skill，把它们的风险并入下面两个固定小节：
   - **`## Deterministic Findings`**：本地 8 维 + 三个子 skill 的确定性发现按严重度合并排序（严重度/Code/指标/值/阈值/证据）；子 skill 来源的那些行证据末尾带 `（详见 gaussdb-lockwait / gaussdb-waitevent / gaussdb-vacuum）`，`维度` 列用的是对应子 skill 自己的维度名（`Locks` / `DB Time` / `Dead Tuples`），不是已经退役的 `Transaction Locks & Blocking Chains` / `Wait Events` / `Dead Tuples & Bloat` 这几个旧名字。
   - **`## Collection Notes`**：哪些本地维度降级、哪个子 skill 采集失败，同一种形式呈现。

   报告顶部还固定带两段，**任何一次运行都会出现，不依赖是否命中风险**：
   - **`## 本次未采集到的维度`**：点名本次哪个子 skill 没采集成功、原因是什么；三个都成功时写清楚"全部采集成功"。
   - **`## 未纳入汇总的能力`**：无条件列出 `gaussdb-explain`、`gaussdb-sqltune`、`gaussdb-sqlreview`、`gaussdb-sqlfetch`、`gaussdb-proctune` 这 5 个 skill——它们都需要用户指定具体 SQL / sql_id / 存储过程才能跑，health 拿不到这类输入，**这 5 项永远不在本报告覆盖范围内**；报告本身会说明这一点，不要等用户问起来才提，也不要因为这次报告很干净就暗示"都查过了"。

   `## Slow SQL` 与 `## Window Top SQL` 已排除 GaussDB 自己的系统 SQL（只访问系统表 / 系统视图 / 系统函数的语句），标题行写着「已排除 N 条内核系统 SQL」，要转告用户。
   `## Slow SQL` 的表只有**已完成**的执行；**还在跑的长 SQL** 由 `SLOWSQL_RUNNING` 报（标题里「执行中超过 5m0s 的 SQL …」，证据带 pid 与 SQL 摘要）。用户问「为什么卡」时先看这一条；标题里「另有 N 条…在等锁」的不是 SQL 慢，是被锁挡住，去锁阻塞那几条找根。
   选项：`--include/--exclude <dims>` 裁剪维度。本地维度名：`overview,slowsql,xact,conn,logs,repl,schema,storage,concurrency`；另外 `locks`、`waits`、`lwlock`、`bloat` 这四个名字继续有效，只是不再对应本地 collector，而是路由到子 skill（`locks`→`gaussdb-lockwait`，`waits`/`lwlock`→`gaussdb-waitevent`，`bloat`→`gaussdb-vacuum`）——已有的命令行不受影响。`--top N` 调列表条数；`--format json` 取结构化（额外带 `sub_skills`、`uncovered_capabilities` 两个字段）。**不要**为某一维度单独多跑命令；也不要看到 `--include locks` 就自己再单独跑一遍 lockwait——health 已经替你跑过了。

   **时段体检（用户说了时间：「最近 30 分钟」「昨天 10 点到 11 点」「10:46 到 11:07」）：**

   ```bash
   python3 {baseDir}/scripts/health.py -c <conn> --window 30m
   python3 {baseDir}/scripts/health.py -c <conn> --from '2026-10-17 10:46' --to '2026-10-17 11:07'
   ```

   时间按**数据库所在时区**；不给 `--to` = 到此刻；不能与 `--include/--exclude` 同用。
   **原则：不追求精确，只把用户说的时间段覆盖住，并告诉用户实际评估的是哪一段、为什么。**
   累计计数器只能在 WDR 快照与「此刻」之间相减，所以实际窗口通常比用户要的宽（宽的部分会摊薄冲高）；
   实例重启过时只能覆盖重启之后那一段。报告第一个维度 `## Evaluation Window` 写着「你要看的是 … 实际评估的是 … 」，
   **回答必须先转达这一句**（要的是哪段、评估的是哪段、为什么，三样不能少），再讲结论。
   - **能回看的**（窗口两端相减）：`## Window Load`（DB time、CPU 占比、平均活跃会话）、`## Window Transactions`
     （提交、回滚、死锁）、`## Window IO / Temp / Checkpoint`、`## Window Waits`（各等待类**占总等待**，
     不是占 DB time —— 等待统计含后台线程，两者口径不同，**不要自己去除**）、`## Window Top SQL`。
   - **锁阻塞从采样回看**：终点在过去时 `## Transaction Locks & Blocking Chains` 由 `gaussdb-lockwait --from/--to`
     读活跃会话采样（ASP）填出阻塞链、根会话与约等了多久（等待时长是「采到次数 × 约 10 秒」的估算，照脚本的「约」说）；
     采样没开 / 过了保留期时这一维标「回看不了」并写明原因。要看全部阻塞对，单独跑同一时段的 lockwait。
     **这一维的处置不给 kill / terminate 语句**：时段已过，当时的会话多半已结束、会话号可能被复用 ——
     处置写「现在还堵着就先跑此刻的锁等待分析」和「改应用的事务边界（开事务不提交）」；
     `idle_in_transaction_session_timeout` 这类参数只能写成「由 DBA 评估」，不要替客户定值。
   - **回看不了的**（瞬时状态，当时没有采）：连接与线程池、长事务、死元组与膨胀、复制、占用量。
     终点在过去时它们逐项标「不可用：回看不了」，**照实说这几项看不了，不要拿此刻的值顶替**；
     终点是此刻时脚本会给**当前值**，标题前缀「【当前值，不是时段内的】」—— 转述时也要带上这个限定。
   - 临时溢出那条发现（`WIN_TEMP_SPILL`）在两端都是快照时会写明**能归到语句的有多少、落盘最多的是哪条**
     （它自己占语句级、占库级各多少，发现里带它的 sql_id）—— 溢出的元凶按这条说，**不要按耗时榜去挑候选**；
     终点是此刻时归不到语句，脚本会说明，这时引导用户对那段时间跑 WDR。
   - 窗口几乎空闲时（`Window Load` 写「窗口几乎空闲」）脚本不判任何比例，**不要自己拿表里的数去算占比再下结论**。
   - 脚本给的大盘链接已经带着这一段（`run=…&from=…&to=…`），原样转给用户。

3. **加载方法论。** 阅读 `{baseDir}/references/gaussdb-health-methodology.md`，逐维度按其检查清单解读，并做跨维度关联。阈值口径查 `{baseDir}/references/health-thresholds.md`。涉及具体慢 SQL 深调时导向 `/gaussdb-sqltune`，存储过程导向 `/gaussdb-proctune`。

4. **逐维度判断。** 对每个维度：解读原始指标、定位根因、做跨维度关联（典型：空闲事务 IIT 持锁 → 阻塞链 + 卡住 vacuum 回收 → 死元组膨胀）。每条结论都要引用证据包里的某个真实数字。

5. **证据锚定校验门（核心，必须做）。** 拿 `## Deterministic Findings` 逐条核对你的判断：
   - **每条结论必须引用一个真实越界指标/发现**；无指标支撑的结论移入「未证实想法」，不进正式发现。
   - **每条 WARN/CRITICAL 确定性发现都必须被你处理**；漏掉的在报告里标 `⚠ 模型遗漏：<Code>`。
   - **你给的严重度必须与确定性带一致**；不一致标 `⚠ 严重度不符（模型 X / 确定性 Y）`，并**以确定性为准**。
   - **总体状态必须等于确定性最差 severity**（`## Deterministic Findings` 里最重的一条）；**你不得下调**。
   产出**判断校验徽章**：`✓ 已锚定（N 条发现全覆盖、无夸大、无遗漏）`，或列出上述偏差。

6. **报告。** 按「## 回答模板」的巡检四段产出(段标题照写),各段放什么:
   - **开头** —— 时段体检先写第 3 步那句评估时段;然后**抬头状态带** `总体状态 <🟢健康/🟡关注/🟠告警/🔴严重>`,附一句「驱动:<最重发现的根因/摘要>」;
     下一行 `判断校验 <徽章>`;再下面一段短结论(2–4 句,开发人员也看得懂)。
   - **① 现象** —— **维度概览矩阵**:本地 8 维各一行:维度、严重度徽章、关键指标(取该维 Headline / 关键数字);三个子 skill 里本次采集成功的,
     各按它贡献的最高严重度补一行(维度名用它自己的:`Locks` / `DB Time` / `Dead Tuples`,注明来源 skill);采集失败的不编一行,
     去 `## 本次未采集到的维度` 里找原因,在本段末尾一句说明。矩阵后用两三句应用视角概括哪几个方面出了问题。
   - **② 根因和证据链** —— 对每条确定性发现(重→轻):**证据**(引用真实指标 vs 阈值)→ **根因**,按「两种读者」各写一小段;
     重要维度的**原始表**(阻塞链树、Top 死元组表、等待 Top)放在对应现象下面当证据;跨维度的因果串成一条链。
     来自子 skill 的发现保留 `（详见 gaussdb-xxx）` 指针(见规则)。
   - **③ 解决方案** —— 用 **P0/P1/P2 文字**标优先级(P0 最优先),每条:改什么、为什么(回指 ② 的哪个现象)、详细做法、`风险:低/中/高`、`[需人工执行]`;
     **不要用严重度 emoji(🔴🟠🟡)当优先级图标**(见规则)。每条行动项必须自带结论正文,见下条规则。
   - **④ 总结和结论** —— 两三句总结 + 下一步建议 + 需要用户配合的事;然后收尾一句:本报告全部经脚本只读采集,所有结论已对确定性发现锚定校验;
     最后是 1–3 条展开提议。

## 退出码

| 退出码 | 含义 |
|---|---|
| 0 | 报告完整：本地 8 个维度与所有纳入范围的子 skill 均采集成功 |
| 1 | 参数/形状被拒绝，或渲染层出错——**没有产出报告** |
| 2 | 连接建立失败——**没有产出报告** |
| 3 | 报告已经完整打印，但至少一个纳入范围的子 skill（锁 / 等待 / 死元组）采集失败——报告顶部 `## 本次未采集到的维度` 会点名是谁、原因是什么 |

**退出码 3 存在的理由：** 一份缺了锁、等待信息却退出 0 的报告，对下游脚本/告警管道而言和一份干净报告没有区别——两者都是 `rc=0`。exit=3 让消费方不用解析报告正文就能从退出码本身分辨"报告完整"与"报告不完整但已经打印"。**报告不会因为退出码非 0 而被截断或省略**——3 是附加信息，不是替代输出；看到 3 时先读 stdout，报告就在那里，只是顶部会点名哪块没查到。

## 规则

- **数值自相矛盾时，先说「这个数不可信」，不要替它编解释。** 例：2026-10-18 那轮测试里，空闲库上
  「LWLOCK 耗时占 DB time 171.8%」、再加 CPU 78.6% 合计 250% —— 各部分之和超过整体，本身就说明分子分母口径不同
  （等待统计含后台线程，DB time 只算前台会话）。当时的回答把它解释成「锁争用严重」，是编的。现在脚本遇到这种情形
  会写明「自相矛盾、不可信」并且不据此判定；你看到类似的数（占比超过 100%、部分之和大于整体、同一指标两处对不上），
  **照实说不可信、说明是哪两个数对不上**，不要挑一种说得通的故事填进去。
- **报告只呈现结论，不呈现推演。** 「等等 / 换个角度」这类自我纠正不得进入报告；若改了判断，回头同步矩阵里的严重度，使报告自洽。
- **只读、绝不执行修复。** health 不执行 `kill` / `pg_terminate_backend` / `VACUUM` / 任何 DML；处置一律只给带风险级的建议，注明 `[需人工执行]`。
- 不要编造统计：每个结论引用脚本输出里的某个数字。
- **来自子 skill 的确定性发现，`（详见 gaussdb-xxx）` 指针是允许的落点，不必展开成全套上下文。** `## Deterministic Findings` 表里带这个后缀的行，是 `gaussdb-lockwait`/`gaussdb-waitevent`/`gaussdb-vacuum` 自己算出来的确定性证据——如实转述该行的 code/指标/值/证据，保留这个指针即可；**不要凭空替它扩写根因分析或具体改法**，那些内容在对应子 skill 自己的报告里，客户要看细节就直接单独跑那个 skill。下面这条「行动项必须自带结论正文」管的是另一种情形：你自己写的处置建议里引用了别的 skill 的结论（比如引用 sqltune 的改写建议），那种指针式引用才是不合格的。
- **行动项必须自带结论正文，不能只留一个指针。** 「推动 sqlid 1136765424 的 sqltune 结论落地」这种写法是不合格的——读的人不知道结论是什么。凡引用别的 skill 或别处的结论，必须一并带上：**是哪条对象**（SQL 原文摘要 / 表名 / 索引名）、**当前状态**（计划形态与代价、扫描次数、页数）、**提议的改动**（哪条索引 / 哪种改写）、**预期效果**、**依据**。跨 skill 引用尤其如此：报告是要发给客户看的，sqlid 在那边解引用不了。
- **累计型指标必须先给观测窗口。** `idx_scan` / `seq_scan` / `n_tup_*` 都是「自上次统计重置以来」的累计值。报告里出现它们时，先写出 `pg_stat_database.stats_reset` 的时间与至今时长——窗口 5 分钟的 `idx_scan=0` 和窗口 7 天的 `idx_scan=0` 是两回事，而两者长得一模一样。
- **区分「观测到的」与「推断的」，措辞不要越界。** 「该索引在当前统计窗口内未被使用」是观测；「无用索引」是关于未来的断言，不要写。同理「统计陈旧」要说清凭哪两个数、差多少、阈值多少。建议删除索引前必须点明三条反例：统计重置或实例重启会让计数归零；月度/季度/年终报表用的索引可以数周为 0；主备分离时备机上的使用不计入本机计数器。
- **总体状态以确定性发现为准**，LLM 不得下调；无确定性发现时才是 🟢健康。
- **优先级与严重度是两个独立维度，分开标。** 确定性严重度用 🟢🟡🟠🔴（脚本定，不可改）；处置优先级用 P0/P1/P2（你按影响排）。一条 🟡 的发现可以因持锁/扩散风险被你排成 P0——这没问题，但呈现时该发现**仍标 🟡，P0 用文字**；**绝不用 🔴 当 P0 小节的图标**，否则会让人误以为存在 critical 级发现。
- 某维度 `## Collection Notes` 标了降级（缺视图/权限）时，如实说明该维度不可用，不要臆测其结论。
- 绝不在对话中回显密码或 DSN。
- 遇到脚本报错，查 `{baseDir}/references/setup.md` 的症状对照表。
- **「累计」与「距上次新增」要分开说,不能只报累计值。**
  死锁数、回滚数是**自上次统计重置以来**的累计值。发生过一次死锁之后这个数永远 > 0,
  于是每次巡检都报「死锁累计数 24」—— 报了三个月、其中两个月零新增,用户分不出
  「正在发生」还是「历史上发生过」,久了当背景噪音,真的新增时也看不见。
  脚本现在会多给两行:`deadlocks 距上次新增`、`回滚率 距上次`(与上一次**完整巡检**相比)。
  - 有「距上次新增」时,**以它为准**回答「现在有没有问题」,累计值只用来说明历史;
    零新增时脚本已经撤掉那条发现,你也不要再把累计值说成当前问题。
  - 写着「统计被重置过,给不出增量」时,**照实说**,不要说成「距上次没有新增」。
  - 给不出增量时脚本写 `deadlocks 距上次新增 | 给不出：<原因>`,DEADLOCKS 那条的证据开头也带着原因。
    原因有几种:第一次巡检(本次留下基线,下次就有)、没有报告存档目录(`GSDB_REPORTS_DIR` 未设置,
    这台机器上**一直**给不出,不要说成「下次就有」)、局部巡检不留基线、统计被重置过。**照脚本的原因转述**,只报累计值。
    基线文件没有时脚本会退回存档里上一份完整巡检报告来算,不用你自己去翻历史报告。
  同理:用户问「最近十分钟的 Top SQL」时,累计榜会把十分钟的冲高摊平,要用
  `gaussdb-topsql --window 10m` 或 `--from/--to`(见那个 skill 的执行规则第 0 条)。
- **死锁的明细在数据库日志里。** 死锁那条发现只有次数;环上是哪几条语句、谁被牺牲,数据库里不留,本工具也读不到日志。
  请用户把日志里含 `deadlock detected` 的那几段(连同后面的 DETAIL 几行)贴过来,然后交给
  `python3 {baseDir}/../gaussdb-lockwait/scripts/lockwait.py --deadlock-log -`(日志段从标准输入给,不连库),
  它会解析出环、语句、牺牲者并按模式给出改法。用户没贴之前,不要从 Top SQL 里挑两条语句说成「就是它们在死锁」。

- **大盘链接原样转给用户。** 完整巡检跑完后，脚本在标准错误里打一行「已存入大盘:/dash/health?inst=…&run=…」，
  在回答末尾附上这个链接。用户说「生成 / 打开 / 看看大盘」时，就跑一次**完整巡检**（不带 `--include/--exclude`，
  局部巡检不存档）再给出这个链接。用户要看**某个时间段内库的情况**，跑时段体检（`--from/--to` 或 `--window`，见工作流第 2 步），
  它给的链接已经筛在那一段上；用户只是要翻看**那段时间里跑过的**巡检报告，才在链接后加
  `&from=2026-10-16T15:00&to=2026-10-16T16:00`（本地时间）——这种筛选不会替你取数。它是给用户看的页面地址（和对话页同一个网址），不是内部接口。
  **脚本给的是 Markdown 链接形态 `[打开报告](…)`，就按这个形态放进回答，不要把它改写成裸路径。** 裸的 `/dash/wdr?...` 用户点不开、复制到地址栏也打不开（实测过：用户要某个时间段的 WDR 报告，拿到裸路径之后跳不过去）。
  没有这一行（非容器环境，或存档失败）就不提大盘，**不要自己拼一个「大盘」地址出来**。

## 2026-10-17 新增的四项判定——读的时候有三件事不能搞混

这四项补的都是**此前完全没有信号**的故障：配置看着正常、连接数正常、没有慢 SQL，
但库会挂住或盘会被填满。

- **`SYNC_COMMIT_NO_STANDBY`（🔴）——「要求同步确认，却一个同步备都没有」。**
  主库的提交会**一直等下去**，表现是写入全部挂住。处置：恢复备库，或由 DBA 临时把
  `synchronous_commit` 降为 `local`。
  **反过来，在单机库上这一项会明说「不适用」，那不等于「健康」。**
  openGauss 的同步复制要靠 `replconninfo` 定义对端才生效 —— og5 实测
  `synchronous_commit=on` + `standby_names='*'` + 零个备库，写入完全正常。
  所以看到「单机部署，同步提交不适用」时，**不要**替它补一句「配置有风险」。

- **`WAL_SLOT_INACTIVE`（🟠）/ `WAL_SLOT_LAG`——复制槽钉住了 WAL 回收。**
  这和 `REPL_LAG` 是**两件事**，处置方向相反：`REPL_LAG` 是备库追不上（看备库），
  这两条是槽不消费、WAL 只增不减直到填满磁盘（看下游消费端，或删掉废槽）。
  未活跃的槽**不看落后量就报** —— 消费端已经没了，落后量现在小但会一直涨，
  而且没有任何东西会自动清掉它。

- **`THREAD_POOL_HIGH`（🟠）——开了线程池时，真正的并发上限是池大小。**
  og5 实测 `max_connections=1000` 而池只有 800，先碰到的是 800。池满后新请求排队，
  现场表现是「库没响应」，而**连接维度此时是绿的** —— 用户说「库没反应」而你看到
  连接数很正常时，先看这一条。占比的分母是 `thread_pool_attr` 的池大小，
  解析不出来时脚本**不判**并说明原因（不会拿 `max_connections` 顶上去当分母）。

- **`STORAGE_LARGE`（🟡/🟠）——只是占用量，不是「盘快满了」。**
  **文件系统剩余空间在这个内核上取不到**（`pg_stat_file` 要 initial account，实测被拒）。
  所以这一维回答的是「哪个库/表空间很大、涨得快」，**回答不了「还剩多少」**。
  转述时必须带上这个边界，并提示用户结合操作系统侧的磁盘监控看 ——
  照着一个取不到的事实说「磁盘即将耗尽」，是在编造证据。

### 开头与结尾(所有回答)

3. **短结论**:2–4 句,先说结论再说原因,开发人员也看得懂;不能出现比总体状态更轻的定性。

### 两种读者(正文每一段都照做)

正文的每一段分两小段,依次以「应用视角:」「数据库机制:」开头:

- **应用视角**(写给开发人员,对数据库不太熟):业务感受到什么(交易超时、接口变慢、批量跑不完),
  应用里哪类写法会导致它。不懂数据库的人也要能看懂。
- **数据库机制**(写给数据库工程师):**接着同一件事、同一批对象**(同一条 SQL、同一张表、同一组会话)往下讲
  为什么会这样 —— 锁、MVCC、WAL、执行计划、参数怎么起作用。不另起话题。

讲机制也要落到这次采到的数字上;没有证据,不提内核参数调整。

### 写法规矩(模板化之后照旧)

- 每条结论引用脚本输出里的一个真实数字;没有数据支撑的不进正式结论。
- 只呈现结论,不呈现推演过程(「等等 / 换个角度」这类自我纠正不进回答)。
- 行动项自带结论正文:改哪个对象、现在什么状态、怎么改、预期效果、依据 —— 不能只留一个指针。
- 问的是过去的时间段时,事后看不到的现象(例如当时的内存上下文分布)写「这一项回看不了」,不拿现在的状态冒充当时;
  能回看的(锁与阻塞链有活动会话采样,见 gaussdb-lockwait 的时段回看)照常回看。

### 本技能的正文:巡检四段

此刻巡检和时段体检都用这四段。开头按「开头与结尾」:时段体检先写评估时段 → 总体状态带 → 短结论。

**① 现象**:多个维度把看到的现象摆出来 —— 维度概览(每维一行:维度、级别、关键数字);没采到的维度不编行,在本段末尾说明。

**② 根因和证据链**:按级别从重到轻,对**每一个**现象逐个写「现象 → 证据(真实数字 vs 阈值;原始表放在这里当证据)→ 根因」。

**④ 总结和结论**:两三句总结 + 下一步建议;需要用户配合的写明;最后是展开提议。

   (贵行规范 / 历史相似 / 本行历史路径 / 处置手册 / 已知缺陷 / 贵行基线 / 产品文档 / Wiki 经验 / 原始工单)。
   先看候选原因:**同一现象本行有过多种根因时,按「区分证据」决定先取哪项证据**,不要看到一单相似就照搬它的处置。
   要看某个专题的全貌用 `kb.py topic <专题>`;不要 `--all` 整个专题全读,除非用户要「全部列出来」。
3. **L2 知识条目——引用前先读**:处置步骤、审批与变更要求、受影响版本、基线数值,**必须出自 `kb.py show <ID>` 读过的条目**;
   摘要只够说「有一条相关规定 / 一单类似案例」。每次回答最多读 5 条,挑与本次发现最相关的。
4. **L3 原始证据——只在四种情况读** `kb.py evidence <ID>`:① 两条知识说法冲突;② 用户要看原文;
   ③ 依据的条目是「推测 / 待验证 / 未验证」却要据此给出高风险操作建议;④ 照片、日志里的数字需要核对。

### 各类知识怎么用

- **处置建议以知识库为首选依据**:客户的先例与口径优先于通用经验——措辞、步骤、变更窗口、审批要求都按客户的来
  (有处置手册先给手册);引用时**必须带 ID 与出处**,写不出 ID 的不要写。
- 某条发现下写着「无对应条款 / 无相似案例 / 路径:无」时,**如实说「知识库中未找到相关内容,以下为通用知识,仅供参考」**,
  不得把通用经验伪装成客户规范或客户案例;**绝不允许编一条客户规范或案例出来**。
- 「本行历史路径」只列客户确认过的因果链,可以直接引用;「原始工单」只是相似原文,只能说「有一单类似,未结构化」。
- 案例结论强度不是「已确认」的(推测 / 待验证)、Wiki 经验是「未验证 / 已过时」的,引用时要带上这个标签。
- **适用性**:条目带〔不适用本环境:…〕的(产品系列、版本、系统与本实例画像不符),**不得作为依据**,最多说明「这是
  openGauss / 其他版本的行为」;带〔未知本环境…〕的(没有画像)引用时说明「适用性未知」。已知缺陷按行里写的
  「本环境 X 受影响 / 不受影响」如实转述。
- **贵行基线**只用来说明「这个数在本行平时是多少」,与脚本阈值并列呈现,**不改 severity**。
- 状态行写「模式:文件(原因)」时:环境里没配或连不上向量库/图库,这一节是**直接在知识库文件上**检索出来的,
  用法与上面完全一样,**不因为是文件模式就放松引用要求**。「图:图文件」同理——只是路径改从文件里走,不是没有路径。
- 状态行写「知识库未接入(原因)」时,不提知识库、不猜原因,按自带知识作答即可。

#### 知识引用写法

出自知识库的内容**直接写进正文**:不写「根据知识库检索」「知识库显示」这类专门交代来源的话,也不在回答里单列一节「客户知识库参照」
(脚本输出里的那一节是给你读的输入,不是回答的版式)。知识问答例外:第一行写「解答来源」。

- **上色**:按「是谁说的」分两种颜色,让用户一眼分清「贵行的规定、先例」和「产品官方说法」——
  贵行自己的知识(规范、案例、手册、缺陷、基线、画像、Wiki)包进 `<font color=#2f6fdb>…</font>`(蓝);
  产品文档(官方文档集 PD-<代号>-<5 位数字>,如 PD-G25132C-01481;以及客户导入的产品文档 PD-NNNN)包进 `<font color=#0f7c86>…</font>`(青)。
- **出处**:标签后面紧跟括号写出处,括号是普通文字 —— 不上色、不加反引号、不加粗。照这个样子写(这一行本身不是代码):

  <font color=#2f6fdb>DDL 变更时会话级锁等待上限不超过 30 秒</font>(引用自贵行规范库 GS-CHG-003)

  库名按类型:

  | 类型 | 编号形如 | 括号里的库名 |
  |---|---|---|
  | 规范 | GS-<域>-NNN | 贵行规范库 |
  | 修正 | 修正条目的编号 | 贵行规范库(修正) |
  | 案例 | S1~S4-<日期>-<系统>-… | 本行案例库 |
  | 手册 | RB-<域>-NNN | 处置手册库 |
  | 缺陷 | KD-NNNN | 已知缺陷库 |
  | 基线 | BL-<系统>-<指标> | 贵行基线库 |
  | 画像 | EP-<系统> | 环境画像库 |
  | 产品文档(客户导入) | PD-NNNN | 产品文档库 |
  | 官方文档集 | PD-<代号>-NNNNN | GaussDB 官方文档库 |
  | Wiki | WK-NNNN | Wiki 经验库 |
  | 原始工单、指南 | 条目给的编号 | 原始工单库、指南库 |

  结论强度是「推测 / 待验证」的案例、「未验证 / 已过时」的 Wiki、「未经演练验证」的手册,把标签写进括号:
  (引用自 Wiki 经验库 WK-0002,未验证)。写不出编号的不要写。
- **标签照抄**:不加引号、不改任何符号(引号写成中文引号、# 前多个空格都会不变色);标签里不用加粗和行内代码(会盖掉颜色)。
  一个标签只包一句话、一个列表项或一个表格单元格,不跨段落、不跨列表项;代码块里不放标签(不变色,还会把标签原样露出来)——
  引用知识库里的命令或 SQL 时,把引出它的那句话上色。
- **不上色**:脚本的诊断结果、你自己的分析、通用经验;拿不准是否出自知识库的,不上色。
- **知识库里没有**:该处要用通用知识时写「知识库中未找到相关内容,以下为通用知识,仅供参考」,不上色;**绝不编造客户规范或案例**。

**规范条款的兜底查法**(kbimport 1.x 沿用,本版仍保留):现行条款逐条清单 `{kbDir}/RULES.md`、案例清单 `{kbDir}/CASES.md`
还在生成,脚本那一节没覆盖到的条款判断可以按清单逐条核对;关键词辅助检索
`grep -rn "<关键词>" {kbDir}/errata {kbDir}/rules {kbDir}/guides {kbDir}/runbooks {kbDir}/defects`
(archive/ **有意**不在范围内)。库内优先级:修正(errata)> 条款(rules)> 其余。
知识库的条款与脚本判定**不一致**时:如实并列呈现两边,交用户裁决;不要自行选边,也不要假装它们一致。
