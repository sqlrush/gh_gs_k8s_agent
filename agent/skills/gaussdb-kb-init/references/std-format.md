# 统一格式(std)——入库前的标准化文档

一单一份 md。frontmatter 记元数据与出处,正文固定四段。**由 `kb_init.py render` 渲染,不要手写。**

```markdown
---
std_version: 1
item_id: "ITSM-2026-000108"
title: "跑批期间 CPU 占用 80% 以上"
occurred_at: "2026-01-08"
system: "F-CIIS"
severity: "S2"
conclusion: "已确认"
objects: ["cbst.cosp_asyn_task_dtl"]
signals: ["跑批时段 CPU>80%"]
source: "【2026-01-08】某行CIIS CPU使用率高问题分析报告.docx"
source_file: "【2026-01-08】某行CIIS CPU使用率高问题分析报告.docx"
source_kind: "docx"
extracted_by: "script"
redacted: 0
---

## 现场

2026 年 01 月 08 日业务执行跑批过程中 CPU 占用 80% 以上，持续约 20 分钟。

## 判断

库中存在执行 20 分钟左右的长事务，死行无法回收；部分表每小时更新删除几十万次，
扫描时可见性判断代价升高，CPU 消耗增加。

## 处置

应急查杀长事务语句；降低跑批过程中 QPS 并发量；高频更新删除的热点表改用全局临时表。

## 复发标志

跑批时段 CPU > 80%，且库中存在 20 分钟以上的长事务、关键表死行数明显高于前一日。
```

## 字段

| 字段 | 必填 | 说明 |
|---|---|---|
| `std_version` | 是 | 格式版本,校验器认它。当前 `1` |
| `item_id` | 否 | 原始工单号。没有就留空,渲染时填 `unknown` |
| `title` | 否 | 一句话标题。留空则取「现场」前 40 字 |
| `occurred_at` | **是** | 发生日期 `YYYY-MM-DD`。认不出来脚本会报错——问用户,不要猜 |
| `system` | **是** | 业务系统名 |
| `severity` | 否 | S1/S2/S3 之类,原文有就写 |
| `conclusion` | 否 | `已确认` 或 `推测`,默认 `推测`。根因是原文写明的才写「已确认」 |
| `objects` | 否 | 原文里出现的对象:表名、GUC、等待事件。用原文叫法,拿不准就留空 |
| `signals` | 否 | 可观测的信号,给复发识别用 |
| `source` | **是** | 出处回指,如 `报告.docx` 或 `工单导出.csv#row=7`。指不回去的不入库 |
| `source_kind` | 是 | 原件类型:`docx` / `pdf` / `csv` / `jpg` … |
| `extracted_by` | 是 | `script`(脚本抽的文本)或 `model`(你看图/读原文写的)。照片一定是 `model` |
| `redacted` | 是 | 脱敏替换次数,`0` 表示没脱敏 |

## 四段正文

段名与顺序**固定**为 `现场 → 判断 → 处置 → 复发标志`,与知识库 `cases/` 的案例格式一致,
所以标准化之后能直接进导入流程。改名或换序会被 `validate` 拦下。

每段都不能为空。原文确实没写的,**显式**写这三种之一:`原文未写明` / `原文未提及` / `未提及`。
`无`、`暂无`、`待补`、`TODO`、`?` 一律被拒绝——它们读起来像结论,实际是空白。

## 为什么是这六个

它们正好回答入库之后检索要回答的问题:

- **时间 / 系统** —— 这条先例是什么时候、哪个系统的,还作不作数;
- **现场** —— 下次遇到类似现象时能不能匹配上;
- **判断** —— 当时认定的原因(以及有没有认定);
- **处置** —— 本行的口径是什么(这才是知识库相对通用知识的价值);
- **复发标志** —— 凭什么认出是同一个问题再次发生。

## 与导入的衔接

`render` 除了 `std/*.md`,还会产出 `out/<批次>-tickets.md`:同样的内容,但每单一块、块间用 `---` 分隔、
**块内不带 frontmatter**。因为 `kb.py ingest` 处理 md 时按 `\n---\n` 切多单,块里再带 frontmatter
会被从中间劈开,变成「半份元数据 + 半份正文」两单。交给导入 skill 的是这个文件。

## 导入侧怎么认这些已定字段

`out/<批次>-tickets.md` 的块里，`- id:` / `- source:` / `- system:` / `- occurred_at:` 不是给人看的注释，
导入 skill 会认它们（`common/kb/ingest.py::std_meta`，判定条件是 `system` 与 `occurred_at` 同时存在）：

| std 块里的 | 进 item frontmatter 后 | 作用 |
|---|---|---|
| `- id:` | `item_id` | 保住客户的原始工单号（否则会被换成 `<批次>-N`，客户拿它跟 ITSM 交叉引用就断了） |
| `- source:` | `source` | **案例最终的出处**。必须指回客户原件；我们的中间文件记在 `ingested_from` 里 |
| `- system:` / `- occurred_at:` / `- severity:` / `- conclusion:` | 同名字段 | `propose` 据此预填工作单的 `known`，`review` 据此核对候选 |

**核对是硬闸门**：候选里这四个字段与标准化文档不一致时，`review` 报 `[error]` 并把两个值都写出来，
要么改候选照抄，要么先改标准化文档再重跑。理由是「两处说法不一」必须当场暴露——静默采用候选那一版，
知识库与交给客户的标准化文档就此分叉，而两边都还看起来正常。

普通材料（客户直接丢进来的 md / 表格）没有这些字段，一切照旧，不会因此多出任何检查。
