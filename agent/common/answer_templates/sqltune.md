### 本技能的正文:SQL 优化四段

开头:总体状态带写「验证状态:已找到已验证方案 / 未找到已验证方案」+「驱动:」一句(主要慢在哪)→
短结论(这条 SQL 平均 / 最大耗时多少、主要慢在哪、推荐方案验证过没有)。

**① 现状与趋势**:照抄脚本的 `## Current Stats`、`## Trend`、`## Plan Changes` 三节 ——
执行次数、平均 / 最大 / 最小耗时(实测);近几天按小时的变化;脚本判出的「突然变慢」时间点;那时执行计划变没变
(变过的给出前后两棵计划)。超出保留期的照抄脚本的说明。**拐点与计划变化以脚本判定为准,不自己拿数去推。**
三节都没有(白名单脚本未登记或取数失败)时写「现状数据暂不可得」及脚本给的原因,其余三段照常。

**② SQL 文本和执行计划解读**:被分析的 SQL → 执行计划(瓶颈节点标 [P1]…)→ 计划走查 → 根因 → 证据链摘要(「慢在哪里」)。

**③ 怎么优化**:每个**已验证**方案写改动、为什么(回指 [P#])、证据、风险,外加**前后对比**:
- SQL 文本差异:改写方案才有,照抄脚本给的差异;
- 执行计划差异:改写方案给前后两棵计划;只建索引、又没有假设索引验证的,如实写「拿不到建索引后的计划」;
- cost:照抄验证结果 `X → Y(N×)`,不自己算;
- 执行耗时:优化前写实测平均(① 里的数);优化后没有实测时写「需实测」,**不拿 cost 倍数换算成耗时**。

没通过验证的放本段末尾「未验证想法」,不和已验证的混放。

**④ 总结**:两三句总结 + 展开提议,其中一条是「需要我给出在测试环境实测的步骤吗?」——
用户实测后把耗时贴回来,再做前后对比。
